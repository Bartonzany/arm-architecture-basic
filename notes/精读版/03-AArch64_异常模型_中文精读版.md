## 导读：这篇文章在讲什么

只要涉及启动代码、内核、虚拟机监控器或固件，就绕不开“异常”和“特权”这两个概念。本指南讨论 Armv8-A 与 Armv9-A 的异常模型和特权模型，重点回答三个问题：

- Arm 架构把异常分成哪几类，各自在什么时机发生；
- 处理器遇到异常时，硬件会自动做哪些事；
- 软件（尤其是低层代码）需要如何配合，才能正确地进入异常、处理异常并返回。

目标读者是编写启动代码、内核或异常管理代码的开发者。读完之后，你应当能够说清各异常级别（EL）的职责、执行状态如何在 AArch32 与 AArch64 之间切换、一个简单的 AArch64 向量表由哪些部分组成，以及异常处理器如何被使用。

## 1. 从“特权”说起

现代软件天然是分层的：操作系统内核和用户应用程序对系统资源的访问能力完全不同。内核需要执行一些应用程序不该执行的操作，因此需要更高的资源访问级别；应用程序则应当受到限制。

这里说的“访问能力”，就是**特权（privilege）**：它决定一个软件实体能看到、能控制哪些处理器资源。

AArch64 通过划分不同的特权级别来支撑这种分层。关键在于：**当前特权级别只在进入异常或从异常返回时才会改变**。正因如此，Arm 把这些特权级别称为“异常级别（Exception level）”。

## 2. 异常级别 EL0–EL3

### 2.1 四个级别与常见软件模型

异常级别通常缩写为 EL，写作 EL\<x\>，其中 \<x\> 取 0 到 3。数字越大，特权越高，EL0 是最低级别。

![图 2-1：异常级别](../../asset/figure2-1-exception-levels.png)

*图 2-1：异常级别*

架构本身并不规定“哪层软件必须跑在哪个 EL”，但业界形成了一套常见模型：

- 应用程序运行在 EL0；
- Linux 这类富操作系统（Rich OS）运行在 EL1；
- 虚拟机监控器（hypervisor）使用 EL2；
- 固件和安全网关代码使用 EL3。

例如，Linux 可以通过软件接口标准调用 EL3 的固件函数，把“给某个核上电或下电”这类低层细节包装成一个更高层的意图。按照这个模型，处理单元（PE）的大部分工作都发生在 EL0/EL1。

架构并不强制这套软件模型，但标准软件普遍假设它成立。因此，本指南后续内容都基于这一模型展开。

### 2.2 什么时候异常级别会改变

异常级别只在以下情况发生时改变：

- 进入异常（taking an exception）；
- 从异常返回（returning from an exception）；
- 处理器复位（processor reset）；
- 进入调试状态（Debug state）；
- 退出调试状态（exiting from Debug state）。

方向上有两条硬规则：

- 进入异常时，EL 可以升高，也可以保持不变，但**绝不会降低**；
- 从异常返回时，EL 可以降低，也可以保持不变，但**绝不会升高**。

换句话说，异常是“向上走”的通道，异常返回是“向下走”的通道。后文还会反复用到这一点。

### 2.3 两种特权视角

与异常模型相关的特权可以分成两类：

- **内存特权**：一次内存访问按特权还是非特权规则检查；
- **寄存器访问特权**：能否访问某些处理器资源，尤其是系统寄存器。

两者都取决于当前所处的 EL。

**内存特权**

Arm A-Profile 实现了虚拟内存系统。MMU 允许软件为内存区域配置属性，其中包括读/写权限，而且可以分别针对特权访问和非特权访问设置不同权限。

规则很直接：

- 在 EL0 执行时发起的内存访问，按**非特权**权限检查；
- 从 EL1、EL2、EL3 发起的内存访问，按**特权**权限检查。

这些内存配置由软件通过 MMU 的转换表（translation table）编程决定。而转换表本身放在内存里，配置 MMU 的系统寄存器也有访问门槛——于是“能不能改内存权限”最终又回到“当前处于哪个 EL”。

**寄存器访问**

AArch64 处理器的配置保存在一组 **系统寄存器（System register）** 中。这些寄存器的取值组合，构成了当前的处理器上下文（processor context）。能否访问它们，由当前 EL 决定。

以 `VBAR_EL1`（向量基址寄存器，Vector Base Address Register）为例。它的用途后文会讲，这里先看后缀 `_EL1`：它表示访问该寄存器至少需要 EL1 特权。

架构中有很多“名字相似、功能相似、只是 EL 后缀不同”的寄存器。它们不是同一个寄存器的不同视图，而是**彼此独立**的寄存器：指令编码不同，硬件实现也各自独立。后缀表示访问所需的**最低**异常级别。

每个已实现的 EL 都有一个系统控制寄存器（SCTLR），用于控制该 EL 下的架构特性，例如 MMU、缓存和对齐检查：

| 寄存器 | 说明 |
| --- | --- |
| `SCTLR_EL1` | EL0 和 EL1 的顶层系统控制 |
| `SCTLR_EL2` | EL2 的顶层系统控制 |
| `SCTLR_EL3` | EL3 的顶层系统控制 |

> EL1 和 EL0 共享同一份 MMU 配置，而控制权限只属于运行在 EL1 的特权代码。因此不存在 `SCTLR_EL0`，相关控制都来自 EL1 可访问的寄存器。其他控制寄存器通常也遵循这一模式。

高 EL 可以访问低 EL 的寄存器。例如，EL2 在需要时可以访问 `SCTLR_EL1`；但 EL0 不能访问它，强行访问会触发异常。

系统正常运行时，各 EL 管理各自的配置；不过在虚拟化、上下文切换等场景下，高 EL 也会主动读写低 EL 的寄存器。

本指南涉及的关键系统寄存器如下：

**表 2-1：处理异常时的关键系统寄存器**

| 寄存器 | 名称 | 描述 |
| --- | --- | --- |
| ELR_ELx | 异常链接寄存器（Exception Link Register） | 保存触发异常的指令的地址 |
| ESR_ELx | 异常综合寄存器（Exception Syndrome Register） | 包含异常原因的信息 |
| FAR_ELx | 故障地址寄存器（Fault Address Register） | 保存虚拟故障地址 |
| HCR_ELx | 虚拟机监控器配置寄存器（Hypervisor Configuration Register） | 控制虚拟化设置以及把异常捕获（trapping）到 EL2 |
| SCR_ELx | 安全配置寄存器（Secure Configuration Register） | 控制安全状态以及把异常捕获到 EL3 |
| SCTLR_ELx | 系统控制寄存器（System Control Register） | 控制标准内存、系统设施，并提供已实现功能的状态信息 |
| SPSR_ELx | 保存的程序状态寄存器（Saved Program Status Register） | 保存异常被送到该 ELx 时处理器的状态 |
| VBAR_ELx | 向量基址寄存器（Vector Base Address Register） | 保存任何被送到 ELx 的异常的异常基址 |

## 3. 执行状态与安全状态

AArch64 提供四个异常级别、两种执行状态（Execution state），以及最多四种安全状态（Security state）。处理器的“当前状态”，由异常级别、执行状态和安全状态共同决定。

### 3.1 执行状态：AArch32 与 AArch64

执行状态决定了通用寄存器的标准宽度、可用的指令集，还会影响内存模型的某些方面以及异常的管理方式。

- **AArch32**：32 位执行状态，与更早的架构向后兼容，支持 T32 和 A32 指令集，标准寄存器宽度为 32 位。
- **AArch64**：64 位执行状态，支持 A64 指令集，标准寄存器宽度为 64 位。

本指南后续重点讨论 AArch64 下的异常处理。

**改变执行状态**

PE 只能在复位时，或异常级别发生变化时，改变执行状态。跨 EL 移动时，还可以在 AArch32 与 AArch64 之间转换，但要遵守两条规则：

- 从低 EL 移动到高 EL：执行状态可以保持不变，或变为 AArch64；
- 从高 EL 移动到低 EL：执行状态可以保持不变，或变为 AArch32。

把两条规则合起来看，就是一句话：**64 位的层可以承载 32 位的层，反之不行**。例如，64 位操作系统内核可以同时运行 64 位和 32 位应用程序；32 位内核则只能承载 32 位应用程序。

![图 3-1：32 位与 64 位层上的异常级别](../../asset/figure3-1-32-64bit-layers.png)

*图 3-1：32 位与 64 位层上的异常级别*

这个例子用的是操作系统和应用程序，但规则对所有 EL 都成立。例如，运行在 EL2 的 32 位虚拟机监控器，只能承载 EL1 上的 32 位操作系统。

Armv8-A 在所有 EL 上都支持 AArch32 和 AArch64，但具体每个 EL 支持哪一种（或两种都支持），由实现自行决定。

对 Armv8-A 处理器而言，复位时的执行状态由“实现定义（IMPLEMENTATION DEFINED）”的机制决定。例如 Cortex-A32 总是复位进入 AArch32。

对 Armv9-A 处理器而言，所有 EL 都必须支持 AArch64；是否在 EL0 支持 AArch32 由实现决定，其他 EL 一律为 AArch64，复位时也始终进入 AArch64。

每个 EL 的执行状态，由**下一个更高且已实现的 EL** 的控制寄存器决定：EL1 看 `HCR_EL2`，EL2 看 `SCR_EL3`。复位时，EL3 的执行状态（如果可切换）由外部引脚决定。这部分在“路由与中断控制器”一节还会展开。

### 3.2 安全状态

AArch64 允许实现多个安全状态，从而把软件进一步分区，隔离出受信任的部分。

大多数 Cortex-A 处理器支持两种安全状态：

- **安全状态（Secure state）**：PE 可以访问安全与非安全物理地址空间，以及寄存器组的“安全”副本。
- **非安全状态（Non-secure state）**：通常也叫 Normal world。PE 只能访问非安全物理地址空间，并且只能访问允许非安全访问的系统寄存器。

安全状态不只是一个标签，它决定了三件事：哪些已实现的 EL 可访问、哪些内存区域可访问，以及这些访问如何体现在系统内存总线上。

一个典型例子是：Android 等操作系统运行在 Normal world，支付或 DRM 系统运行在 Secure world。后者的可信度要求更高，必须与前者隔离，以保护支付信息、密钥等敏感数据。两种安全状态正好提供了这种隔离。

![图 3-2：使用不同执行状态的异常级别与安全状态](../../asset/figure3-2-security-states.png)

*图 3-2：使用不同执行状态的异常级别与安全状态*

安全状态的使用细节见《TrustZone for AArch64》指南。

**改变安全状态**

如果实现了 TrustZone，处理器处于安全还是非安全状态，由 `SCR_EL3.NS` 位选择。

注意上图中 EL3 处于安全状态。EL3 是特权最高的 EL，其安全状态是固定的，并且 EL3 能访问所有被分组（banked）系统寄存器的副本。

在 Armv8-A 中，EL3 始终处于安全状态。在 Armv9-A 中，EL3 属于安全状态的一部分，除非实现了 RME（Realm Management Extension）。实现 RME 后，Root 状态会把 EL3 与其余安全状态隔离开来，下一节会展开。

无论从哪个安全状态切到另一个，都必须经过 EL3。EL3 软件负责管理对各安全状态的访问，是名副其实的“看门人（gatekeeper）”：它控制 EL2、EL1、EL0 能进入哪种安全状态。`SCR_EL3.NS` 位决定了从 EL3 返回时是否改变安全状态。

> 在 EL0、EL1、EL2，PE 既可以处于安全状态，也可以处于非安全状态。常见写法有：
>
> - `NS_EL1`：非安全状态，异常级别 1
> - `S_EL1`：安全状态，异常级别 1

**Realm Management Extension（RME）**

Armv9-A 引入了 RME。实现 RME 后，会额外支持两种安全状态：

- **Realm 状态（Realm state）**：PE 可以访问非安全和 Realm 物理地址空间。
- **Root 状态（Root state）**：PE 可以访问所有物理地址空间。Root 状态仅在 EL3 可用。

RME 把 EL3 与所有其他安全状态隔离开。于是 EL3 不再属于普通的安全状态，而是进入自己的 Root 状态。EL3 承载平台和初始启动代码，因此必须同时被 Secure、Non-secure 和 Realm 软件信任。

![图 3-3：启用 RME 的 PE 中的安全状态](../../asset/figure3-3-rme-security-states.png)

*图 3-3：启用 RME 的 PE 中的安全状态*

更多内容见《Realm Management Extension》。

### 3.3 已实现异常级别带来的影响

具体处理器实现哪些 EL、每个 EL 允许哪些执行状态，都属于实现选择。

其中，**EL0 和 EL1 是必须实现的**，EL2 和 EL3 是可选的。

如果省略 EL2 或 EL3，需要留意后果：

- EL2 承载大量虚拟化功能。没有 EL2，就无法使用这些特性。详见《AArch64 virtualization》指南。
- EL3 是唯一能改变安全状态的级别。如果实现中省略 EL3，该 PE 就只能停留在单一安全状态，具体停在哪个状态由实现决定。

有些软件明确要求平台提供这些级别。例如 KVM Linux 需要 EL2、EL1 和 EL0。

> 在 Armv8.0-A 中，EL2 只存在于非安全状态，因为当时安全状态下没有虚拟化支持。Armv8.4-A 把 S.EL2 作为可选特性加入，并用使能位 `SCR_EL3.EEL2` 保持向后兼容。到了 Armv9-A，只要支持 EL2，就必须在两种安全状态中都支持它，不过禁用位仍然存在。

Armv8-A 处理器可以自行决定每个 EL 允许哪些执行状态（实现定义）。有一条约束：**如果某个 EL 允许 AArch32，那么所有更低的 EL 也必须允许 AArch32**。例如 EL3 允许 AArch32，则 EL2、EL1、EL0 也都必须允许。

许多实现支持全部执行状态和全部 EL，但也存在受限的实现，例如：

- Cortex-A35：所有 EL 都支持 AArch32 和 AArch64；
- Cortex-A32：只支持 AArch32；
- Neoverse-N2：EL0 支持 AArch32，其他 EL 仅支持 AArch64。

AArch32 用于兼容旧的 32 位软件。从 Armv9-A 起，它被限制为仅在 EL0 可选实现：AArch64 在所有 EL 都支持，AArch32 只在 EL0 可选。这意味着可以继续运行遗留应用，但内核、虚拟机监控器和固件都必须是 64 位。

具体某颗芯片支持哪些 EL，应以该处理器的技术参考手册（TRM）为准。

## 4. 异常是什么

异常是需要特权软件介入处理的条件或系统事件：它可能要求补救，也可能只是要求更新系统状态，以保证系统继续平稳运行。更直观地说，**任何导致当前程序被挂起的事件，都可以归入异常**。进入异常意味着状态切换，处理器转去执行处理该异常的代码。

![图 4-1：处理异常](../../asset/figure4-1-handling-an-exception.png)

*图 4-1：处理异常*

其他架构有时把这类事件统称为“中断（interrupt）”。在 AArch64 中，中断只是异常的一种——一种由外部产生的外部异常。

异常的用途很多，例如：

- 模拟虚拟设备；
- 虚拟内存管理；
- 处理软件错误；
- 处理硬件错误；
- 调试；
- 发起跨特权或跨安全状态的调用；
- 处理中断（定时器、设备交互）；
- 处理不同执行状态之间的交互（interprocessing）。

进入异常时，处理器不会继续执行当前代码的下一条指令，而是停下当前执行流，跳到专门处理该请求的代码。这段代码叫**异常处理器（exception handler）**。处理完成后，执行可以返回原程序。每种异常类型都有自己的异常处理器，如图 4-1 所示。

Arm 架构把异常分成两大类：**同步异常（synchronous exceptions）**和**异步异常（asynchronous exceptions）**。

## 5. 同步异常

同步异常由当前正在执行的指令引起，或与它直接相关。所谓“同步”，是指异常与指令流严格对齐：比如一条指令试图写入 MMU 标记为只读的位置，就会触发同步异常。

判断一个异常是否为同步，要看三个条件是否同时成立：

- 它是直接执行（或尝试执行）某条指令的结果；
- 异常处理完后要返回的地址，与触发异常的指令之间存在架构定义的关系；
- 它是 **精确（precise）** 的：进入处理器时看到的寄存器状态，必须等价于“违规指令之前的指令全部执行完、之后的指令一条都没执行”。

同步异常类型很多，同一条指令也可能触发多种同步异常。Arm 架构为它们规定了固定的优先级顺序。

下面看几类常见成因。

### 5.1 无效指令与陷阱异常

执行无效指令会产生同步异常。所谓无效，可能是指令本身 UNDEFINED，也可能是当前 EL 不允许执行，或者该指令已被禁用。任何“内核无法识别”的指令执行尝试，都会产生 UNDEFINED 异常。

架构还允许控制实体（操作系统或虚拟机监控器）设置**陷阱（trap）**，拦截低 EL 的某些操作。当被监视的动作发生时，陷阱就会触发异常。

一个典型场景是惰性上下文切换（lazy context-switching）。EL1 内核可以暂时禁止 EL0 使用浮点/SIMD 指令，这样在应用之间切换时就不必每次都保存庞大的 SIMD/FP 寄存器组；只有真正用到时，才通过陷阱异常补做保存。

具体做法是：内核先禁用 SIMD/FP 单元，并监视其状态。一旦有 FP 或 SIMD 指令执行，就会向 EL1 送入陷阱异常。内核此时再启用该单元、重新执行那条失败的指令，并置一个标志表示“用过了”。这样下次上下文切换就必须把 SIMD/FP 寄存器纳入上下文；如果标志未置位，就可以跳过。

这种捕获能力对虚拟化尤其重要，详见《AArch64 virtualization》。

### 5.2 内存访问引发的异常

同步异常也可能来自内存访问：要么是 MMU 检查不通过，要么是内存系统返回了错误。

MMU 启用后，所有加载/存储指令引发的内存访问都要经过检查。比如非特权代码访问特权地址，或试图写只读地址，MMU 会阻止访问并触发 MMU 故障（fault）。由于这类错误是同步的，异常会在内存访问继续之前被送入。

内存访问错误的更多细节见《AArch64 memory management》。

内存访问也可能产生异步异常，也就是后文要讲的 SError。

> 在 AArch64 中，同步中止（synchronous abort）导致同步异常；异步中止（asynchronous abort）导致 SError 中断异常。

### 5.3 主动产生异常的指令：SVC、HVC、SMC

有些指令的存在意义就是产生异常，用于实现系统调用接口，让低特权软件向高特权软件请求服务。

Arm 架构提供三条这样的指令：

- **SVC**（Supervisor Call）：EL0 用户程序请求 EL1 操作系统服务；
- **HVC**（Hypervisor Call）：操作系统请求 EL2 虚拟机监控器服务；需要实现虚拟化扩展；
- **SMC**（Secure Monitor Call）：Normal world 请求 EL3 固件的 Secure world 服务；需要实现安全扩展。

它们唯一的用途就是产生异常，并让 PE 在 EL 之间移动。

当 PE 处于 EL0 时，不能直接调用 EL2 的虚拟机监控器或 EL3 的安全监控器——那只能从 EL1 及以上发起。EL0 应用必须先执行 `SVC` 请求内核，再由内核代它向更高 EL 发起调用。

假设相应级别已实现，EL1 内核可以执行 `HVC` 调用 EL2，或执行 `SMC` 调用 EL3；EL2 也可以执行 `SMC` 调用 EL3。如下图所示：

![图 4-2：服务调用路由](../../asset/figure4-2-service-call-routing.png)

*图 4-2：服务调用路由*

还要记住：异常不能被送入更低的 EL。因此在 EL2 执行 `SVC`，不可能“返回”到 EL1。

> 如“无效指令与陷阱异常”所述，虚拟机监控器可能正在向 EL1 呈现一个模拟的系统视图。此时客户操作系统（guest OS）无法直接用 SMC 调用设备固件，这类调用会被 `HCR_EL2.TSC` 位捕获到 EL2。

### 5.4 调试异常

调试异常属于同步异常，会被路由到承载调试器的 EL。调试器代码的处理方式与普通异常处理器类似。

常见的同步调试异常包括：

- 断点指令异常（Breakpoint Instruction exceptions）；
- 断点异常（Breakpoint exceptions）；
- 观察点异常（Watchpoint exceptions）；
- 向量捕获异常（Vector Catch exceptions）；
- 软件单步异常（Software Step exceptions）。

更多内容见《AArch64 self-hosted debug》。

## 6. 异步异常

异步异常由外部产生，与当前指令流不同步。

它和正在执行的指令没有直接关系，通常来自处理器外部的系统事件，比如定时器到期或屏幕被触摸。我们无法预知它何时到来。

按定义，**不是同步异常的，就是异步异常**。异步异常也叫中断（interrupt）。

进入异步异常时，程序流被打断，转去执行处理该外部请求的代码。架构不保证异常在哪一刻被送入，只要求它在一个有限时间内发生。

### 6.1 物理中断

物理中断响应 PE 外部的信号，通常由外设产生。与其让内核不停轮询外部信号，不如让设备在需要时“敲门”——这个“敲门”就是中断。

以 UART 为例：当它收到数据，需要通知处理器“新数据到了，可以处理了”。产生一个中断，就是最直接的信号机制。

复杂系统可能有多个中断源，优先级各不相同，还支持嵌套：高优先级中断可以打断低优先级中断的处理。内核响应这类事件的速度，是系统设计中的关键指标，称为**中断延迟（interrupt latency）**。

### 6.2 SError

系统错误（System Error，SError）是一种专门用来报告内存系统意外事件的异常。我们不希望这类事件发生，但一旦发生必须知道。它之所以异步报告，是因为触发事件的指令可能已经提交（retired），无法再回到那条指令上精确处理。

SError 的典型前身是“外部异步中止（external asynchronous abort）”。常见例子包括：

- 内存访问通过了所有 MMU 检查，却在内存总线上出错；
- RAM 的奇偶校验或 ECC 检查失败，例如内置缓存中的 RAM；
- 缓存行把脏数据写回外部内存时触发中止。

SError 被视为独立的一类异步异常，因为通常需要为它准备专门的处理程序。是否产生 SError 由实现定义。

### 6.3 IRQ 与 FIQ

Arm 架构用 **IRQ** 和 **FIQ** 两种异步异常来支持外设中断。它们负责传递“定时器触发”这类外部事件，而不是报告系统错误；它们是预期之内、相对指令流异步的事件。

IRQ 和 FIQ 有独立的路由控制，通常用来区分安全与非安全中断，具体参见《Arm Generic Interrupt Controller v3 and v4》。两者各自怎么用，由实现定义。

> 在旧版 Arm 架构中，FIQ 是优先级更高的“快速中断”。AArch64 不是这样：FIQ 与 IRQ 优先级相同。

几乎所有系统都会把 AArch64 处理器与中断控制器搭配使用，由后者汇总、定优先级并分发中断。Arm 实现普遍采用通用中断控制器（GIC）架构来管理 IRQ 和 FIQ。GIC 负责中断管理、优先级判定和路由，对每种物理中断类型只向内核提供单一信号。

### 6.4 虚拟中断

引入虚拟化后，中断处理变得更复杂：有些中断该由虚拟机监控器处理，有些则应交由虚拟机（VM）内部处理。VM 看到的中断就是**虚拟中断**。

虚拟中断既可以由连接到中断控制器的设备从外部产生，也可以由软件产生。为此，AArch64 对虚拟中断提供了显式支持：

- **vSError**：虚拟系统错误；
- **vIRQ**：虚拟 IRQ；
- **vFIQ**：虚拟 FIQ。

三类虚拟中断分别控制，功能与对应的物理中断相同，但它们只能向 EL1 发信号。

虚拟中断可以由 EL2 的虚拟机监控器产生，也可以借助中断控制器产生。虚拟机监控器必须设置 `HCR_EL2` 中相应的路由位。例如要启用 vIRQ，就要设置 `HCR_EL2.IMO`：它一方面把物理 IRQ 路由到 EL2，另一方面允许向 EL1 发出虚拟异常信号。

`HCR_EL2` 中控制虚拟中断产生的三个位如下：

| 位 | 说明 |
| --- | --- |
| VSE | 设置此位即注册一个 vSError |
| VI | 设置此位即注册一个 vIRQ |
| VF | 设置此位即注册一个 vFIQ |

设置其中某一位，效果相当于中断控制器向某个 vCPU 断言了一个中断信号。这种做法的代价是：虚拟机监控器必须在 VM 内模拟中断控制器的行为，频繁操作时开销可观。因此更推荐直接使用中断控制器。

GICv2 及更高版本同时提供物理 CPU 接口和虚拟 CPU 接口，可以分别发送物理中断和虚拟中断。安全状态下的虚拟化支持在 Armv8.4-A 中加入，并要求启用并支持安全 EL2。

### 6.5 屏蔽与不可屏蔽中断

物理和虚拟异步异常都可以被暂时屏蔽。被屏蔽的异常会停在挂起（pending）状态，直到解除屏蔽后才被送入。这对处理嵌套异常特别有用。

同步异常不能被屏蔽，因为它直接由指令执行引起；若把它挂起或忽略，执行就会被卡住。

2021 年的扩展（Armv8.8-A 和 Armv9.3-A）加入了不可屏蔽中断（NMI）支持。启用后，某些中断可以以“超级优先级（Superpriority）”呈现给处理器：即使普通屏蔽位处于屏蔽状态，这类中断仍能被送入。

屏蔽与 NMI 的细节会在“异常处理”与“异常屏蔽”部分继续展开。

## 7. 异常处理全流程

上一章说明了异常有哪些类型。这一章把镜头拉近，看异常从发生到返回，硬件和软件各做了什么。

先统一术语：

- PE 响应一个异常，叫“送入（taken）”异常；
- PE 进入异常之前的状态，是该异常“从之被送入（taken from）”的状态；
- PE 进入异常之后的状态，是该异常“被送入到（taken to）”的状态。

因此，“从 AArch32 EL0 向 AArch64 EL1 送入异常”这句话，就把来源状态和目标状态都说清楚了。

处理完毕后需要返回，这叫**异常返回（Exception return）**，由专门指令触发：

- PE 执行返回指令时所处的状态，是“从之返回（returns from）”的状态；
- 返回指令执行完之后的状态，是“返回到（returns to）”的状态。

### 7.1 进入异常时硬件做了什么

异常发生时，处理器先保存 PE 的当前状态和返回地址，然后进入处理该异常的模式。

具体来说，PSTATE 会做一份快照，写入保存的程序状态寄存器（SPSR）；返回地址写入异常链接寄存器（ELR）。对于同步异常和 SError，还会更新异常综合寄存器（ESR），记录异常原因。

当异常被送入一个使用 AArch64 的 ELx 时，硬件会完成以下动作：

- 把进入异常前的 PSTATE 写入 `SPSR_ELx`；
- 把首选的异常返回地址写入 `ELR_ELx`；
- 对同步异常和 SError，把异常综合信息（原因）写入 `ESR_ELx`；
- 对与地址相关的同步异常（如 MMU 故障），把触发异常的虚拟地址写入 `FAR_ELx`。

然后，处理器跳转到**异常向量（exception vector）**——一个固定的内存地址，开始执行处理代码。

> AArch64 的向量表和许多其他架构不同：表里存放的是**指令**，不是地址。每个表项最多 32 条指令，刚好够做基本的压栈并跳转到具体处理代码。

向量表通常先执行一段通用动作，再按异常类型跳到后续处理代码，如图 5-1 所示。这段向量代码被限制在 32 个字（word）以内；真正的异常处理器则包含完整处理逻辑以及从异常返回的代码。

![图 5-1：顶层处理器](../../asset/figure5-1-top-level-handler.png)

*图 5-1：顶层处理器*

每种异常都有目标 EL。因此，进入异常可以实现向不同 EL 的路由。这一点很关键，因为**获得特权的唯一途径就是进入异常，失去或降低特权的唯一途径就是异常返回**。

由此可以推出：

- 进入异常时，EL 保持不变或升高；
- 异常返回时，EL 保持不变或降低。

注意，进入异常或执行返回，并不一定意味着 EL 改变——目标 EL 可能就是当前 EL。目标 EL 要么由异常类型隐式决定，要么由系统寄存器中的配置位决定。

> 在 AArch64 中，你只能从 EL0 向更高 EL 送入异常。异常永远不会被送入 EL0，EL0 也没有向量表。

执行状态同样只在复位或异常进出时改变。AArch32 与 AArch64 之间的交互称为 interprocessing。规则与前面一致：

- 低 EL → 高 EL：执行状态保持不变，或变为 AArch64；
- 高 EL → 低 EL：执行状态保持不变，或变为 AArch32。

架构还规定：

- 如果某个 EL 使用 AArch32，则所有更低的 EL 都必须使用 AArch32；
- 如果某个 EL 使用 AArch64，则所有更高的 EL 都必须使用 AArch64。

在 Armv9-A 以及部分 Armv8-A 实现中，AArch32 仅在 EL0 受支持，而异常不能送入 EL0。因此要改变 EL0 的执行状态，必须先进入更高 EL，再返回。

由于异常可以从 AArch32 送入 AArch64，AArch64 的处理代码可能需要访问 AArch32 寄存器。AArch32 通用寄存器会直接映射到 AArch64 寄存器：

**表 5-1：AArch32 到 AArch64 的寄存器映射**

| AArch32 | AArch64 |
| --- | --- |
| R0–R12 | X0–X12 |
| Banked SP 和 LR | X13–X23 |
| Banked FIQ | X24–X30 |

从 AArch32 切到 AArch64 时，AArch32 状态下不可访问的寄存器会保留此前 AArch64 执行时的值。对于两种状态都能访问的寄存器，从使用 AArch32 的 EL 送入异常时，64 位寄存器的高半部分有两种可能：

- 高 32 位：UNKNOWN；
- 低 32 位：所映射的 AArch32 寄存器值。

AArch64 寄存器的细节见《AArch64 Instruction Set Architecture》。

### 7.2 保存当前处理器状态

AArch64 用 **PSTATE** 表示处理器状态，SPSR 保存的就是它的快照。PSTATE 包含当前异常级别、ALU 标志等信息，具体包括：

- 条件标志（Condition flags）；
- 执行状态控制（Execution state controls）；
- 异常屏蔽位（Exception mask bits）；
- 访问控制位（Access control bits）；
- 时序控制位（Timing control bits）；
- 推测控制位（Speculation control bits）。

其中与异常屏蔽直接相关的是 DAIF 四位。某位被置 1，对应类型的异常就不会被送入：

- **D**：调试异常屏蔽位；
- **A**：SError 异步异常屏蔽位（如异步外部中止）；
- **I**：IRQ 异步异常屏蔽位；
- **F**：FIQ 异步异常屏蔽位。

进入异常时必须保存当前状态，以便之后能准确返回。PE 会自动保存返回地址和 PSTATE。前面说过，PSTATE 快照写入 SPSR。

每个 EL 都有自己的 SPSR，即 `SPSR_ELx`。异常送入哪个 EL，就更新哪个：送入 EL1，就更新 `SPSR_EL1`。

保存完成后，PE 按架构对该异常类型的定义更新 PSTATE，反映新的 EL 和安全状态。

> 在 Armv7 及更早版本中，PSTATE 称为 CPSR，并且被实现为一个寄存器。

PSTATE 更新后，PE 就可以跳到向量表中的异常处理器。执行从目标 EL 的对应向量开始。要返回时，处理器把 SPSR 的内容恢复到 PSTATE，并跳转到 ELR 中记录的返回地址，如图 5-2 所示。

![图 5-2：保存和恢复处理器状态](../../asset/figure5-2-saving-restoring.png)

### 7.3 路由与中断控制器

每种异常都有目标 EL，这个目标要么由异常类型隐式确定，要么由系统寄存器中的配置位决定。异常的目标由架构固定，或由软件通过路由控制配置。唯一不变的规则是：**异常永远不会送入 EL0**。

同步异常的路由与产生它的 `SVC`、`HVC`、`SMC` 绑定。其他类型的异常，在相应级别已实现时，可以路由到 EL2（虚拟机监控器）或 EL3（安全监控器）。IRQ、FIQ、SError 分别设置路由。例如，某个实现可以把所有 IRQ 都路由到 EL1：

![图 5-3：IRQ 路由示例](../../asset/figure5-3-irq-routing.png)

*图 5-3：IRQ 路由示例*

路由由 `SCR_EL3` 和 `HCR_EL2` 配置：`SCR_EL3` 指定哪些异常路由到 EL3，`HCR_EL2` 指定哪些路由到 EL2。

因此不同中断类型可以走向不同 EL。例如 IRQ 交给 EL1 的操作系统处理，而 SError 更常交给运行在 EL3 的固件处理。

两个寄存器中都有独立的位，分别控制 IRQ、FIQ 和 SError。发生冲突时，`SCR_EL3` 的路由配置优先于 `HCR_EL2`。这些路由位在复位后的值是 UNKNOWN，必须由软件初始化。

常见做法是用 GIC 完成中断管理、优先级判定和路由，这能显著降低虚拟化相关的开销。

> 异常不能送入未实现的 EL，对未实现 EL 的调用是 UNDEFINED。类似地，当 EL2 被禁用或未实现时，为某个安全状态返回到 EL2，会在 ERET 时产生故障。

前面提到异步异常可以被屏蔽并保持挂起。路由会影响屏蔽能力，因为能否屏蔽取决于当前 EL 与目标 EL 的关系：

- 路由到**更高** EL 的异常，无法被较低 EL 屏蔽。例如 EL1 屏蔽了中断，但某中断被路由到 EL2，那么 EL1 的屏蔽不影响 EL2 的送入。不过要注意，EL2 中断可能在 PE 上次退出 EL2 时已被屏蔽，这仍可能导致进入 EL2 时该中断处于屏蔽状态。
- 路由到**当前** EL 的异常，可以被当前级别屏蔽。
- 路由到**更低** EL 的异常，始终被屏蔽。异常会挂起，直到 PE 降到不高于目标 EL 的级别。这与“进入异常不会失去特权”的规则一致。

**表 5-2：异常级别变化时的屏蔽规则**

| 异常级别变化 | 对屏蔽的影响 |
| --- | --- |
| 目标 EL > 当前 EL | 不可被当前 EL 屏蔽 |
| 目标 EL < 当前 EL | 隐式屏蔽 |
| 目标 EL == 当前 EL | 由 PSTATE 屏蔽位设置 |

异常送入的目标 EL 使用哪种执行状态，由更高的 EL 决定。假设所有 EL 都已实现，对应关系如下：

**表 5-3：根据目标异常级别确定执行状态**

| 被送入到的异常级别 | 执行状态由谁决定 |
| --- | --- |
| EL1 | `HCR_EL2.RW` |
| EL2 | `SCR_EL3.RW` |
| EL3 | EL3 的复位状态 |

### 7.4 AArch64 向量表

向一个使用 AArch64 的 EL 送入异常时，处理器会在向量表中找到入口。向量表是一块普通内存区域，里面存放处理各类异常的指令。

异常发生时，内核需要先执行一段“分发（dispatch）”代码：识别异常原因，再调用对应处理逻辑。存放这些入口的内存位置就是异常向量，AArch64 把它们集中放在异常向量表中。

每个 EL 都有自己的向量表，基址由 `VBAR_EL<x>` 指定（x 为 1、2、3）。EL0 没有向量表，因为异常永远不会送入 EL0。

所有向量表格式相同。根据异常类型以及异常从何处送入，表项被分成不同类别，每个类别在距基址固定偏移处有一个入口。

选择哪个表项，取决于以下因素：

- 异常类型（SError、FIQ、IRQ、同步）；
- 异常从哪个 EL 送入、送入哪个 EL；
- 需要支持哪些执行状态；
- 使用的是哪个栈指针（见“栈指针选择”）。

> VBAR 在复位后的值未定义，必须在使能中断之前配置好。

各表项相对向量基址的偏移如下：

**表 5-4：向量表偏移**

| 地址 | 异常类型 | 描述 |
| --- | --- | --- |
| VBAR_ELx + 0x780 | SError/VSError | 来自更低 EL，且所有更低 EL 均为 AArch32 |
| VBAR_ELx + 0x700 | FIQ/vFIQ | 同上 |
| VBAR_ELx + 0x680 | IRQ/vIRQ | 同上 |
| VBAR_ELx + 0x600 | 同步 | 同上 |
| VBAR_ELx + 0x580 | SError/VSError | 来自更低 EL，且至少一个更低 EL 为 AArch64 |
| VBAR_ELx + 0x500 | FIQ/vFIQ | 同上 |
| VBAR_ELx + 0x480 | IRQ/vIRQ | 同上 |
| VBAR_ELx + 0x400 | 同步 | 同上 |
| VBAR_ELx + 0x380 | SError/VSError | 来自当前 EL，且使用 SP_ELx |
| VBAR_ELx + 0x300 | FIQ/vFIQ | 同上 |
| VBAR_ELx + 0x280 | IRQ/vIRQ | 同上 |
| VBAR_ELx + 0x200 | 同步 | 同上 |
| VBAR_ELx + 0x180 | SError/VSError | 来自当前 EL，且使用 SP_EL0 |
| VBAR_ELx + 0x100 | FIQ/vFIQ | 同上 |
| VBAR_ELx + 0x080 | IRQ/vIRQ | 同上 |
| VBAR_ELx + 0x000 | 同步 | 同上 |

特权软件把这些信息记录到系统寄存器中，内核才能在异常发生时定位入口。整个表先按来源分成两组，每组再按栈指针分成两个子组：

- 来自更低 EL 的异常
  - 更低 EL 使用 AArch32
  - 更低 EL 使用 AArch64
- 来自当前 EL 的异常
  - 使用 SP_ELx 的情况
  - 使用 SP_EL0 的情况

因此，从异常落在哪个向量，本身就能推断出异常发生时处理器的部分状态。栈指针选择的含义见下一节。

这里有个容易忽略的细节：从更低 EL 报告的执行状态，指的是目标 EL **紧邻下方**那个 EL 的执行状态，而不一定是异常来源 EL。例如异常从 EL0 送入 EL1，向量按 EL1 的执行状态选择；但如果异常从 EL0 送入 EL2，则看的是 EL1，而不是 EL0。原因在于，EL2 通常运行虚拟机监控器，它管理的是 EL0/EL1 上的 VM，需要知道 VM 内操作系统的执行状态，却通常不需要关心操作系统上应用的状态。也有一些例外，例如 `HCR_EL2.TGE` 为 1 的情况，详见《AArch64 virtualization》。

一个简单的异常处理器会先把所有可破坏（corruptible）寄存器压栈——根据异常类型，这可能就是全部寄存器——然后调用具体处理代码。返回时恢复这些寄存器，再执行异常返回指令（ERET）。

向量表每个表项 32 个字的空间，刚好够完成压栈、调用具体处理程序、恢复寄存器并执行 ERET。这一流程如图 5-4 所示。

### 7.5 栈指针选择与栈指针寄存器

在 AArch64 中，架构允许在两个栈指针之间选择：`SP_EL0` 或 `SP_EL<x>`（x 为当前 EL）。例如在 EL1，可以选择 `SP_EL0` 或 `SP_EL1`。上一节的向量表已经体现了这种区分。

进入异常时，目标 EL 的栈指针 `SP_ELx` 会被自动选中。PE 的选择规则由 PSTATE 配置：

- 在 EL0 执行：使用 `SP_EL0`。
- 在 EL1、EL2、EL3 执行：由 `PSTATE.SP` 决定。
  - `PSTATE.SP = 0`：使用 `SP_EL0`；
  - `PSTATE.SP = 1`：使用当前 EL 的栈指针 `SP_ELx`。

进入向量表的第一级处理程序时，使用的是 `SP_ELx`，默认应当用它保存寄存器上下文。之后通常会切换到 `SP_EL0` 做进一步处理。

`SP_ELx` 的栈用于保存那些可能被异常处理器破坏的寄存器，以便返回时恢复。它在处理栈溢出引发的异常时尤其有用，因为能保证有一个有效的栈可用。返回时再反向操作。

举个例子：PE 在 EL1 执行时收到 IRQ 信号，触发 IRQ 异常。若 IRQ 已路由到 EL1，则默认使用 `SP_EL1`（除非 `PSTATE.SP` 另行配置），执行从 `VBAR_EL1 + 0x280` 开始。

这种双栈设计把“异常进入与高层异常处理”的栈，和其他线程（例如栈用量很大的 C 代码）的栈隔离开。`SP_EL0` 通常分配了更大的栈空间，所以在后续处理中往往是更好的选择。更重要的是，异常进入不再依赖主栈的状态。表 5-4 中专门为这种切换准备了不同的向量表项。

正如上一节提到的，异常落在哪个向量，本身就携带了状态信息。例如异常进入和退出期间，异常本应处于屏蔽状态，因此“来自当前 EL 且使用 SP_ELx”这一区域的代码只会在非常特殊的情况下触发。该分组内出现异步异常，通常意味着发生了需要立即处理的严重系统错误，例如内核恐慌（kernel panic）。

### 7.6 从异常返回

异常处理器完成工作后，处理器返回异常发生前正在运行的代码。步骤只有两步：

1. 恢复此前压栈的可破坏寄存器；
2. 执行异常返回指令（ERET）。

ERET 会从对应的 SPSR 恢复处理器状态，并跳转到 ELR 中记录的返回地址。返回后的 EL 由 `SPSR_EL<x>` 中的值决定，其中 x 是“从之返回”的级别；目标执行状态也保存在 SPSR 中。

> `SPSR_ELx` 中指定的执行状态必须与 `SCR_EL3.RW` 或 `HCR_EL2.RW` 的配置一致，否则会产生非法异常返回。

执行 ERET 时，PSTATE 从 `SPSR_ELx` 恢复，PC 更新为 `ELR_ELx` 的值。这两个更新是原子的，处理器不会停在“只恢复了一半”的未定义状态。

每个 EL 的 ELR 保存首选的返回地址，具体取值由异常类型决定：

- 同步服务调用（如 `SVC`）：返回地址是调用指令之后紧邻的那条指令；
- 其他同步异常：返回地址是产生异常的那条指令；
- 异步异常：返回地址是异常送入时尚未执行完的第一条指令。

处理器在需要时可以根据异常类型修改 `ELR_ELx` 的内容。

### 7.7 端到端示例

下面从整体视角看两个例子，一个同步、一个异步。

**同步异常：从 AArch32 EL0 发起系统调用**

假设 EL0 上运行 AArch32 应用，它需要向 EL1 的 AArch64 内核申请堆内存。应用执行 `SVC` 发起系统调用，随后发生以下过程：

- 当前 PSTATE 快照写入 `SPSR_EL1`；
- 首选返回地址（下一条指令）写入 `ELR_EL1`；
- 异常综合信息（原因）写入 `ESR_EL1`；
- 通过 `HCR_EL2.RW` 确定目标执行状态；
- 更新 PSTATE，EL 变为 EL1，执行状态变为 AArch64；
- 跳到 `VBAR_EL1 + 0x600`。这是同步异常，且来自更低 EL、所有更低 EL 均为 AArch32；
- 压栈保存约定的寄存器，维护上下文；
- 从 `ESR_EL1` 识别出异常类型为 SVC；
- 执行 SVC 专用处理代码；
- 处理完成后返回顶层处理器；
- 恢复此前压栈的寄存器，执行 ERET；
- 从 `SPSR_EL1` 恢复 PSTATE（包括返回 EL0、恢复 AArch32 执行状态），PC 更新为 `ELR_EL1` 的值。

本例中，AArch64 处理代码可能需要访问 AArch32 寄存器。

再看一个更复杂的场景：EL0 的非安全（NS）AArch64 应用需要调用 EL1 的安全可信操作系统。由于切换安全状态必须经过 EL3，而 EL0 又不能直接发起 SMC，实际流程是：NS.EL0 先用 `SVC` 进入 NS.EL1；NS.EL1 再执行 `SMC` 进入 EL3，由 EL3 完成安全状态切换并转到 S.EL1。细节见《TrustZone for AArch64》。

**异步异常：在 AArch32 EL0 收到 IRQ**

异步异常（中断）对 PE 和当前指令流而言是外部的。架构不定义它何时被送入，因此它与其他异常之间的优先级由实现决定。

假设 PE 正在 AArch32 EL0 运行应用，此时发生 IRQ，且 `HCR_EL2` 和 `SCR_EL3` 已把 IRQ 路由到 AArch64 EL1：

*图 5-5：简单的异常处理器示例*

- 当前 PSTATE 快照写入 `SPSR_EL1`；
- 首选返回地址（尚未执行完的第一条指令）写入 `ELR_EL1`；
- 通过 `HCR_EL2.RW` 确定目标执行状态；
- 更新 PSTATE，EL 变为 EL1，执行状态变为 AArch64；
- 跳到 `VBAR_EL1 + 0x680`。这是 IRQ，且来自更低 EL、所有更低 EL 均为 AArch32；
- 压栈保存约定的寄存器；
- 执行 IRQ 专用处理代码；
- 处理完成后返回顶层处理器；
- 恢复寄存器并执行 ERET；
- 从 `SPSR_EL1` 恢复 PSTATE（返回 EL0、恢复 AArch32），PC 更新为 `ELR_EL1` 的值。

注意，IRQ 本身并不区分中断来源（定时器还是 UART）。在使用 GIC 的系统中，可以读取 GIC 的中断确认寄存器（IAR）来识别：读取会返回中断 ID，并把该中断标记为活动（active）。处理完毕后，再写 GIC 的中断结束寄存器（EOIR），把状态清回非活动（inactive）。

### 7.8 异常屏蔽与 NMI

上面的例子是最简单的情形。实际系统常常需要临时屏蔽其他中断，避免它们打断正在处理的异常。物理和虚拟异步异常都可以被暂时屏蔽并保持挂起，直到解除屏蔽后才送入。实现方式就是：先屏蔽同类中断，稍后再显式使能。

当处理器向 AArch64 执行状态送入异常时，`PSTATE.DAIF` 会被自动设置。DAIF 分别代表 Debug、Abort（即 SError）、IRQ、FIQ；字段共 4 位，每位对应一类异常。把某位置 1，就屏蔽该类异常——它可以挂起，但不会被处理。在软件清除该位之前，PE 不会跳转到该类的异常处理器。

中断总是只在“被送入的那个 EL”上被屏蔽。同步异常不能被屏蔽，因为它直接由指令执行引起；若挂起或忽略，执行就会阻塞。

路由到更高 EL 的异步异常无法被屏蔽。软件可以在较低 EL 设置 PSTATE 屏蔽位，但拦不住它。例如把 FIQ 路由到 EL3（`SCR_EL3.FIQ=1`）后，在 EL1 或 EL2 把 `PSTATE.F` 置 1 并不会阻止该中断送入。

路由到更低 EL 的异常则始终被屏蔽，与 PSTATE 无关。例如 IRQ 被路由到 EL2/EL1（`SCR_EL3.IRQ=0`）时，只要 PE 处于 EL3，IRQ 就是隐式屏蔽的。

如果软件要支持嵌套异常——比如让高优先级异常打断低优先级异常的处理——就必须显式重新使能中断。通常要等可破坏寄存器压栈完成后，再允许嵌套。

不可屏蔽中断（NMI）支持随 Armv8.8-A 和 Armv9.3-A 的 2021 年扩展加入。具有超级优先级的中断被归类为 NMI，即使 PSTATE 屏蔽位本来会阻止送入，它也能被送入。

NMI 也有约束。首次送入中断异常时，所有中断（包括 NMI）都会被屏蔽，以便软件在可能被后续中断覆盖之前保存状态。

有些时刻软件完全不能处理任何中断，包括 NMI。为此架构增加了新的 PSTATE 屏蔽位 ALLINT，让软件可以在三种状态间选择：

- 不屏蔽任何中断；
- 屏蔽大多数中断，但不包括 NMI；
- 屏蔽所有中断，包括 NMI。

NMI 支持有三种模型，由系统控制寄存器选择：

- `SCTLR_ELx.NMI = 0`：禁用 NMI 支持，中断用 `PSTATE.I` 和 `PSTATE.F` 屏蔽；
- `SCTLR_ELx.NMI = 1`：启用 NMI 支持。
  - `SCTLR_ELx.SPINTMASK = 0`：NMI 由 `PSTATE.ALLINT` 屏蔽；
  - `SCTLR_ELx.SPINTMASK = 1`：NMI 由 `PSTATE.ALLINT` 屏蔽；此外，当目标 EL 使用 `SP_ELx` 时也会被屏蔽。

NMI 支持要求中断控制器能够呈现超级优先级中断。若使用 Arm 的 GIC，该能力从 GICv3.3 和 GICv4.2 开始提供。

Arm 的相关博客对 A-Profile 的 NMI 支持有更详细的介绍。

## 8. 知识自测

**Armv8-A 必须实现哪些异常级别？**

EL0 和 EL1 是强制要求；EL2 和 EL3 可选，但大多数设计都会实现。

**AArch64 有哪两种执行状态？**

AArch32 和 AArch64。

**进入异常时使用哪个栈？**

硬件自动选择 `SP_ELx`，从而提供一个独立、安全的异常栈。

**AArch64 的向量表是如何实现的？**

PE 把表基址保存在 `VBAR_ELx` 中；表本身是一段指令内存，每个表项最多 32 条指令。
