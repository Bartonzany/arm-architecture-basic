## 1. 概述

本指南介绍 AArch64 中的内存翻译（memory translation），这是内存管理的关键。它解释了虚拟地址如何翻译为物理地址、翻译表格式，以及软件如何管理翻译后备缓冲器（TLB）。

此信息对任何开发低层代码（如启动代码或驱动程序）的人都很有用。它对任何编写代码来设置或管理内存管理单元（MMU）的人尤其相关。

在本指南末尾，你可以检验你的知识。你将学到虚拟地址是如何翻译为物理地址的。你将能够说出不同的地址空间，并描述地址空间如何映射到翻译的各个阶段。你还将学到软件何时必须执行 TLB 维护，以及 TLB 维护命令的语法。

## 2. 什么是内存管理？

内存管理描述系统中对内存的访问是如何被控制的。无论是操作系统还是应用程序，每次访问内存时，硬件都执行内存管理。内存管理是一种动态地将内存区域分配给应用程序的方式。

### 2.1 为什么需要内存管理？

应用处理器被设计用于运行富操作系统（如 Linux），并支持虚拟内存系统。在处理器上执行的软件只看到虚拟地址，处理器将其翻译为物理地址。这些物理地址被呈现给内存系统，并指向内存中的实际物理位置。

## 3. 虚拟地址和物理地址

使用虚拟地址的好处是，它允许管理软件（如操作系统）控制呈现给应用软件的内存视图。操作系统可以控制什么内存可见、该内存在哪个虚拟地址可见，以及允许对该内存进行什么访问。这允许操作系统对应用程序进行沙箱化（将一个应用程序的资源对另一个应用程序隐藏），并提供对底层硬件的抽象。

使用虚拟地址的另一个好处是，操作系统可以将多个碎片化的物理内存区域呈现为单个连续的虚拟地址空间给应用程序。

虚拟地址也惠及软件开发者，他们在编写应用程序时不会知道系统的确切内存地址。有了虚拟地址，软件开发者无需关心物理内存。应用程序知道，由操作系统和硬件协同工作来执行地址翻译。

在实践中，每个应用程序可以使用自己的一组虚拟地址，这些地址将映射到物理系统中的不同位置。当操作系统在不同应用程序之间切换时，它会重新编程映射。这意味着当前应用程序的虚拟地址将映射到内存中正确的物理位置。

虚拟地址通过映射翻译为物理地址。虚拟地址和物理地址之间的映射存储在翻译表（有时称为页表）中，如下图所示：

![图 3-1：显示虚拟地址和物理地址的图](../../asset/figure3-1-virtual-physical-addresses.png)

*图 3-1：显示虚拟地址和物理地址的图*

## 4. 内存管理单元（MMU）

内存管理单元（MMU）负责将软件使用的虚拟地址翻译为内存系统中使用的物理地址。

MMU 包含以下内容：

- 表遍历单元（table walk unit），它包含从内存读取翻译表的逻辑。
- 翻译后备缓冲器（TLB），它缓存最近使用的翻译。

软件发出的所有内存地址都是虚拟的。这些内存地址被传递给 MMU，MMU 检查 TLB 中是否有最近使用的缓存翻译。如果 MMU 没有找到最近缓存的翻译，表遍历单元从内存读取适当的表项，如下所示：

![图 4-1：显示 MMU 的图](../../asset/figure4-1-mmu.png)

*图 4-1：显示 MMU 的图*

虚拟地址必须在内存访问发生之前翻译为物理地址（因为我们必须知道我们正在访问哪个物理内存位置）。这种翻译的需求也适用于缓存数据，因为在 Armv6 及更高版本的处理器上，数据缓存使用物理地址存储数据（物理标记的地址）。因此，地址必须在缓存查找完成之前被翻译。

> 架构是一种行为规格说明。缓存必须表现得如同它们是物理标记的。实现可能做不同的事情，只要这对软件不可见即可。

### 4.3 多级翻译

在单级查找中，虚拟地址空间被划分为大小相等的块。在实践中，使用表的层次结构。

第一张表（Level 1 表）将虚拟地址空间划分为大块。此表中的每个表项可以指向一个大小相等的物理内存块，也可以指向另一张表，后者将该块细分为更小的块。我们称这种类型的表为“多级表”。这里我们可以看到一个有三级的多级表示例：

![图 4-4：显示多级翻译的图](../../asset/figure4-4-multilevel-translation.png)

*图 4-4：显示多级翻译的图*

在 Armv8-A 中，级别的最大数量是六级，级别编号为 -2 到 3。

这种多级方法允许描述更大的块和更小的块。大块和小块的特性如下：

- 大块比小块需要更少的读取级别来翻译。此外，大块在 TLB 中缓存更高效。
- 小块给软件对内存分配更细粒度的控制。然而，小块在 TLB 中缓存效率较低。缓存效率较低是因为小块需要跨多个级别的多次读取来翻译。

为了管理这种权衡，操作系统必须在大映射的效率与小映射的灵活性之间取得平衡，以获得最佳性能。

> 处理器在开始表查找时并不知道翻译的大小。处理器通过执行表遍历来计算出正在翻译的块的大小。

因为存在多个虚拟地址空间，指定一个地址在哪个地址空间中很重要。例如，NS.EL2:0x8000 指的是非安全 EL2 虚拟地址空间中的地址 0x8000。

### 5.1 物理地址

除了多个虚拟地址空间，AArch64 还有多个物理地址空间（PAS）：

- 非安全 PAS
- 安全 PAS
- Realm PAS（仅 Armv9-A）
- Root PAS（仅 Armv9-A）

一个虚拟地址可以映射到哪个或哪些物理地址空间，取决于处理器当前的安全状态。以下列表显示了安全状态及其相应的虚拟地址映射目的地：

- 非安全状态：虚拟地址只能映射到非安全物理地址。
- 安全状态：虚拟地址可以映射到安全或非安全物理地址。
- Realm 状态：虚拟地址可以映射到 Realm 或非安全物理地址。
- Root 状态：虚拟地址可以映射到任何物理地址空间。

当 PE 处于可以访问多个物理地址空间的安全状态时，翻译表项控制使用哪个输出物理地址空间。下图显示了多个物理地址空间的映射：

### 5.2 地址大小

AArch64 是 64 位架构，但这并不意味着所有地址都是 64 位的。

### 5.3 虚拟地址的大小

虚拟地址以 64 位格式存储。因此，加载指令（LDR）和存储指令（STR）中的地址总是在 X 寄存器中指定。然而，X 寄存器中并非所有地址都是有效的。

此图显示了 AArch64 中虚拟地址空间的布局：

![图 5-4：虚拟地址的大小](../../asset/figure5-4-size-of-va.png)

*图 5-4：虚拟地址的大小*

EL0/EL1 虚拟地址空间有两个区域：按照惯例，它们被用作内核空间和应用程序空间。这两个区域显示在图的左侧，内核空间在顶部，应用程序空间（标记为“User space”）在地址空间的底部。内核空间和用户空间有单独的翻译表，这意味着它们的映射可以保持分开。

对于所有其他异常级别，地址空间底部有一个单一区域。该区域显示在图的右侧，是单个空间框。

> 如果你将 HCR_EL2.E2H 设置为 1，它会启用一种配置，其中 Host OS 在 EL2 运行，Host OS 的应用程序在 EL0 运行。在这种场景下，EL2 也有一个上部和一个下部区域。

地址空间的每个区域大小最多为 55 位。然而，每个区域可以独立缩小到更小的大小。TCR_ELx 寄存器中的 TnSZ 字段控制虚拟地址空间的大小。例如，此图显示 TCR_EL1 控制 EL0/EL1 虚拟地址空间：

![图 5-5：虚拟地址空间](../../asset/figure5-5-va-space.png)

*图 5-5：虚拟地址空间*

虚拟地址大小编码为：

```
虚拟地址大小（字节） = 2^(64 - TCR_ELx.TnSZ)
```

虚拟地址大小也可以表示为地址位数：

```
地址位数 = 64 - TnSZ
```

因此，如果 TCR_EL1.T1SZ 设置为 32，EL0/EL1 虚拟地址空间中内核区域的大小是 2^32 字节（0xFFFF_FFFF_0000_0000 到 0xFFFF_FFFF_FFFF_FFFF）。任何在配置范围之外的地址，在被访问时，将生成一个异常作为翻译故障（translation fault）。这种配置的优点是，我们只需要描述我们想要使用的尽可能多的地址空间，从而节省时间和空间。例如，想象操作系统内核的内核空间需要 1GB 的地址空间（30 位地址大小）。如果操作系统将 T1SZ 设置为 34，那么只会创建描述 1GB 的翻译表项，因为 64 - 34 = 30。

> 所有 Armv8-A 实现都支持 48 位虚拟地址。对 52 位或 56 位虚拟地址的支持是可选的，由 ID_AA64MMFR2_EL1 报告。在撰写本文时，没有任何 Arm Cortex-A 处理器支持 52 位虚拟地址。

### 5.4 物理地址的大小

物理地址的大小是实现定义的，最大为 56 位。ID_AA64MMFR0_EL1 寄存器报告处理器实现的大小。对于 Arm Cortex-A 处理器，这通常是 40 位或 44 位。

> 在 Armv8.0-A 中，物理地址的最大大小是 48 位。这在 Armv9.3-A 中扩展到 56 位。

### 5.5 中间物理地址的大小

如果你在翻译表项中指定的输出地址大于实现的最大值，内存管理单元（MMU）将生成一个异常作为地址大小故障。

IPA 空间的大小可以像虚拟地址空间一样配置。VTCR_EL2.T0SZ 控制大小。可以配置的最大大小与处理器支持的物理地址大小相同。这意味着你不能配置比受支持的物理地址空间更大的 IPA 空间。

### 5.6 地址空间标识符 —— 用所属进程标记翻译

许多现代操作系统有似乎都从相同地址区域运行的应用程序，这就是我们描述的用户空间。在实践中，不同的应用程序需要不同的映射。这意味着，例如，VA 0x8000 的翻译取决于当前正在运行的应用程序。

理想情况下，我们希望不同应用程序的翻译在翻译后备缓冲器（TLB）中共存，以避免在上下文切换时进行 TLB 失效。但处理器如何知道使用哪个版本的 VA 0x8000 翻译？在 AArch64 中，答案是地址空间标识符（ASID）。

对于 EL0/EL1 虚拟地址空间，可以使用翻译表项属性字段中的 nG 位将翻译标记为全局（Global，G）或非全局（Non-Global，nG）。例如，内核映射是全局翻译，应用程序映射是非全局翻译。全局翻译适用于当前正在运行的任何应用程序。非全局翻译只适用于特定应用程序。

非全局映射在 TLB 中用 ASID 标记。在 TLB 查找时，将 TLB 项中的 ASID 与当前选择的 ASID 进行比较。如果它们不匹配，则不使用该 TLB 项。此图显示了内核空间中不带 ASID 标记的全局映射，以及用户空间中带 ASID 标记的非全局映射：

![图 5-6：翻译后备缓冲器](../../asset/figure5-6-tlb-asid.png)

*图 5-6：翻译后备缓冲器*

该图显示多个应用程序的 TLB 项被允许在缓存中共存，ASID 决定使用哪个项。

ASID 存储在两个 TTBRn_EL1 寄存器之一中。通常 TTBR0_EL1 用于用户空间。因此，单个寄存器更新可以同时改变 ASID 和它所指向的翻译表。

> 2023 年，Arm 引入了同时指定两个 ASID 的能力。从 Armv9.5-A 起，软件可以选择同时使用两个 TTBRn_EL1 寄存器中的 ASID 字段。TTBR0_EL1.ASID 应用于虚拟地址空间下部部分的地址，TTBR1_EL1.ASID 应用于上部部分的地址。

ASID 标记在 EL2 中也可用，当 HCR_EL2.E2H==1 时。

### 5.7 虚拟机标识符 —— 用所属 VM 标记翻译

EL0/EL1 翻译也可以用虚拟机标识符（VMID）标记。VMID 允许来自不同 VM 的翻译在缓存中共存。这与 ASID 对不同应用程序翻译的工作方式类似。在实践中，这意味着一些翻译将同时用 VMID 和 ASID 标记，并且两者都必须匹配才能使用 TLB 项。

> 当某个安全状态支持虚拟化时，EL0/EL1 翻译总是用 VMID 标记——即使未启用 Stage 2 翻译。这意味着如果你正在编写初始化代码并且不使用 hypervisor，在设置 Stage 1 MMU 之前设置一个已知的 VMID 值是很重要的。

### 5.8 Common not Private

如果系统包含多个处理器，一个处理器上使用的 ASID 和 VMID 在其他处理器上是否具有相同的含义？

对于 Armv8.0-A，答案是它们不必具有相同的含义。没有要求软件在多个处理器上以相同方式使用给定的 ASID。例如，ASID 5 可能在一个处理器上被计算器使用，在另一个处理器上被网络浏览器使用。这意味着一个处理器创建的 TLB 项不能被另一个处理器使用。

在实践中，软件不太可能在不同处理器上以不同方式使用 ASID。更常见的是，软件在给定系统中的所有处理器上以相同方式使用 ASID 和 VMID。因此，Armv8.2-A 在翻译表基址寄存器（TTBR）中引入了 Common not Private（CnP）位。当设置 CnP 位时，软件承诺在所有处理器上以相同方式使用 ASID 和 VMID，这允许一个处理器创建的 TLB 项被另一个处理器使用。

> 我们一直在谈论处理器，然而，从技术上讲，我们应该使用术语处理单元（Processing Element，PE）。PE 是实现 Arm 架构的任何机器的通用术语。它在这里很重要，因为存在微架构上的原因，说明为什么在处理器之间共享 TLB 会很困难。但在多线程处理器内，每个硬件线程都是一个 PE，共享 TLB 项则更可取。

> 第 0-2 级表描述符的编码与第 3 级页描述符相同。这种编码允许“递归表”，它指向它们自己。这很有用，因为它使计算特定页表项的虚拟地址变得容易，以便更新它。

## 7. 翻译颗粒

翻译颗粒（translation granule）是可以描述的最小内存块。不能描述比它更小的东西，只有更大的块（颗粒的倍数）。

AArch64 支持三种不同的颗粒大小：4KB、16KB 和 64KB。

处理器支持的颗粒大小是实现定义的，由 ID_AA64MMFR0_EL1 报告。所有 Arm Cortex-A 处理器都支持 4KB 和 64KB。所选的颗粒是最后一级表中可以描述的最小块。也可以描述更大的块。下表显示了基于所选颗粒的每一级表的不同块大小：

| 表的级别 | 4KB 颗粒（每项大小） | 4KB（索引位） | 16KB 颗粒（每项大小） | 16KB（索引位） | 64KB 颗粒（每项大小） | 64KB（索引位） |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 512GB | 47:39 | 128TB | 47 | – | – |
| 1 | 1GB | 38:30 | 64GB | 46:36 | 4TB | 51:42 |
| 2 | 2MB | 29:21 | 32MB | 35:25 | 512MB | 41:29 |
| 3 | 4KB | 20:12 | 16KB | 24:14 | 64KB | 28:16 |

> 在引入 Armv9.2-A 和 Armv8.7-A 之前，使用 52 位地址有限制。当所选颗粒为 4KB 或 16KB 时，最大虚拟地址区域大小为 48 位。类似地，输出物理地址限制为 48 位。只有当使用 64KB 颗粒时，才能使用完整的 52 位。

> TCR_EL1 有两个独立的字段控制内核空间和用户空间虚拟地址范围的颗粒大小。这些字段称为内核空间的 TG1 和用户空间的 TG0。程序员的一个潜在问题是，这两个字段有不同的编码。

### 7.1 地址翻译的起始级别

颗粒和虚拟地址空间的大小共同控制地址翻译的起始级别。

前面的表总结了每一级表中每种颗粒的块大小（单个表项覆盖的虚拟地址范围大小）。从块大小，你可以算出虚拟地址的哪些位用于索引每一级表。

以 4KB 颗粒为例。此图显示了 4KB 颗粒用于索引不同级别表的位：

![图 7-1：翻译的起始级别](../../asset/figure7-1-starting-level.png)

*图 7-1：翻译的起始级别*

想象一下，对于某个配置，你将虚拟地址空间的大小 TCR_ELx.T0SZ 设置为 32。那么虚拟地址空间的大小（以地址位计）计算为：

```
64 - T0SZ = 32 位地址空间（地址位 31:0）
```

如果我们再看前面的 4KB 颗粒图，第 0 级由位 47:39 索引。对于 32 位地址空间，这些位存在但为零。因此，你的配置的翻译起始级别是第 1 级。

接下来，想象你将 T0SZ 设置为 34：

```
64 - T0SZ = 30 位地址空间（地址位 29:0）
```

这一次，你没有其他位用于索引第 0 级表或第 1 级表，所以你的配置的翻译起始级别是第 2 级。

如前面的图所示，当虚拟地址空间的大小减小时，你需要更少的表级别来描述它。

> 这些示例基于使用 4KB 颗粒。同样的原理适用于使用 16KB 和 64KB 颗粒，但地址位会改变。

### 7.2 控制地址翻译的寄存器

地址翻译由系统寄存器的组合控制：

- **SCTLR_ELx**
  - M —— 启用内存管理单元（MMU）。
  - C —— 启用数据和统一缓存。
  - EE —— 翻译表遍历的字节序。
- **TTBR0_ELx 和 TTBR1_ELx**
  - BADDR —— 翻译表起始的物理地址（PA）（或 EL0/EL1 的中间物理地址 IPA）。
  - ASID —— 非全局翻译的地址空间标识符。
- **TCR_ELx**
  - PS/IPS —— PA 或 IPA 空间的大小，最大输出地址大小。
  - TnSZ —— 表覆盖的地址空间大小。
  - TGn —— 颗粒大小。
  - SH/IRGN/ORGN —— MMU 表遍历使用的可缓存性和可共享性。
  - EPDn —— 禁用对特定表的表遍历。
- **MAIR_ELx**
  - Attr —— 控制 Stage 1 表中的类型和可缓存性。

### 7.3 MMU 禁用

当某个翻译阶段的 MMU 被禁用时，所有地址都被平坦映射（flat-mapped）。平坦映射意味着输入和输出地址相同。

## 8. TLB 与翻译变更

当 MMU 启用时，所有数据访问和指令取指都由 MMU 翻译并检查权限。为了避免每次访问都要重新遍历表，处理器将最近使用的翻译缓存在翻译后备缓冲器（TLB）中。

![图 8-1：显示 MMU 的图](../../asset/figure8-1-mmu.png)

*图 8-1：显示 MMU 的图*

> TLB 是翻译的缓存，而不是翻译表的缓存。区别很微妙。有几个寄存器字段控制如何解释翻译表项。TLB 项中的内容是在遍历表时，给定配置下对翻译表项的解释。在《Arm Architecture Reference Manual (Arm ARM)》中，这样的寄存器字段被描述为“允许被缓存在 TLB 中”。

如果你改变一个翻译表项，或影响表项如何解释的控制项，那么你需要使 TLB 中受影响的项失效。如果你不使这些项失效，那么处理器可能会继续使用旧的翻译。

### 8.1 更新翻译

处理器不允许将导致以下任何故障的翻译缓存到 TLB 中：

- 翻译故障（未映射的地址）。
- 地址大小故障（地址超出范围）。
- 访问标志故障。这通常意味着，当使无效翻译变为有效时，不需要 TLBI 维护。

当取消映射一个有效翻译，或改变一个当前有效的翻译时，需要 TLBI 维护。

这是一个取消映射的例子：

```asm
STR X11, [X1]  ; 更新翻译表项，将位置标记为无效
DSB ISH        ; 确保翻译表遍历能看到更新
TLBI VAE1, X10 ; 假设我们在 EL1
DSB ISH        ; 确保 TLB 失效完成
ISB            ; 在此 PE 上同步上下文
; 此时可以依赖新的翻译表项，并且所有由本观察者使用旧映射
; 生成的访问都已完成
```

这是一个将有效翻译改变为不同有效翻译的例子：

```asm
STR X11, [X1]  ; 移除先前的映射，将位置标记为无效
DSB ISH        ; 确保翻译表遍历能看到更新
TLBI VAE1, X10 ; 假设我们在 EL1
DSB ISH        ; 确保 TLB 失效完成
; 现在内部可共享域中的任何观察者中都不存在旧翻译的缓存副本。
; 此时任何访问虚拟地址的尝试都会导致翻译故障，
; 因为没有有效的映射。
STR X11, [X2]  ; 将新映射写入翻译表项
DSB ISH        ; 确保翻译表遍历能看到更新
; 不需要 TLBI，因为不允许 TLB 缓存导致翻译故障的翻译
```

这种方法被称为先破坏后建立（Break Before Make，BBM）。它首先取消映射旧翻译，如前一个例子那样执行必要的 TLBI 维护，然后创建新翻译。这种方法确保在任何时间点都不会有观察者使用旧映射和新映射的混合。

如果软件不能正确管理翻译表的更新，可能导致 TLB 包含同一地址的多个缓存翻译。或者，系统中的不同观察者使用不同版本的翻译。

有些情况下 BBM 不可取。例如，通过系统 MMU（SMMU）连接的设备可能对接受故障并重新尝试访问的容忍度较低。

FEAT_BBMx 增加了在无需使用 BBM 的情况下改变翻译大小的支持。这种能力在将多个页映射融合为单个块映射、或将块映射拆分为单个页映射时很有用。

不同级别的支持是可能的，支持情况通过 ID_AA64MMFR2_EL1 报告：

- Level 0：软件必须使用先破坏后建立。
- Level 1：增加对 nT 属性的支持。
- Level 2：增加保证：改变表或块大小不会破坏一致性、排序保证或单处理器语义，也不会无法清除独占监视器。
- Level 3：同 Level 2，但保证改变块或表大小不会导致 TLBI 被报告。

对于 BBM Level 1 及以上，nT 属性可以用于使融合过程更高效。为了说明 nT 位的使用，我们看一个页融合的例子。

![图 8-2：显示页融合的图](../../asset/figure8-2-page-fusing.png)

*图 8-2：显示页融合的图*

最初，虚拟地址区域被映射为一组页映射。所映射的内存在输入和输出地址空间中都是连续的，这意味着单个块映射是可能的，而且可能更高效。我们将把页映射融合为单个块映射。为此，我们将：

1. 用块描述符覆盖 L2 表中现有的表描述符，nT=1。
   - a. 设置 nT 位告诉处理器，它可能遇到此区域的多个 TLB 项。
2. 使 TLB 失效，以移除任何剩余的融合前缓存翻译。
3. 清除 nT 位。
   - a. 此时，此区域不应有 TLB 项冲突的风险。
4. 使 TLB 失效，以移除任何仍然设置了 nT 位的缓存翻译。

与传统先破坏后建立相比，此流程的优点是翻译区域在任何时候都不是无效的。

使用 BBM L2 及以上，不需要带 nT 的序列，处理器可以处理翻译大小的变化（如融合或拆分）。

### 8.2 TLB 操作的格式

TLBI 指令用于使 TLB 中的项失效。此指令的语法是：

```
TLBI{P} {R}<type><level>{IS|OS} {, <Xt>, <Xt2>}
```

其中：

- `{P}` —— 参数是在单个寄存器还是一对寄存器中指定。
  - Xt2 仅用于操作的 P 变体。
- `{R}` —— 操作是否针对地址范围（指定为基址和大小）。
- `<type>` —— 使哪些项失效。
  - All —— 所有项
  - VA —— 匹配 Xt 中的 VA 和 ASID 的项
  - VAA —— 匹配 Xt 中的 VA、任何 ASID 的项
  - ASID —— 匹配 Xt 中 ASID 的任何项
  - 以及更多
- `<level>` —— 在哪个地址空间上操作。
  - E1 = EL0/1 虚拟地址空间
  - E2 = EL2 虚拟地址空间
  - E3 = EL3 虚拟地址空间
- `<IS|OS>` —— 操作是内部可共享（IS）还是外部可共享（OS）。
  - 当操作加上 IS 时，它被广播到内部可共享域中的其他内核。
  - 当操作加上 OS 时，它被广播到外部可共享域中的其他内核（在 Armv8.4-A 中添加）。
- `<Xt>` —— 在哪个地址或 ASID 上操作。仅用于按地址或 ASID 的操作。

考虑，例如，一个操作系统正在更新其内核翻译表中的表项。一个典型的 TLB 失效序列会如下所示：

```asm
STR  X1, [X5]        // 写入翻译表项
DSB  ISH             // 屏障指令 - 本指南不涵盖
TLBI VAAE1IS  , X0   // 使 X0 指定的 VA 失效，在 EL0/1
                     // 虚拟地址空间中，针对所有 ASID
DSB  ISH             // 屏障指令 - 本指南不涵盖
ISB                  // 在此处理器上同步上下文
```

### 8.3 TLBI 域

本章介绍 TLBI 域（FEAT_TLBID），作为 Armv9.7-A 的一部分添加。

如前所述，当现有翻译被改变时，通常需要 TLB 失效操作来移除旧翻译的缓存副本。这些失效操作需要在任何可能缓存了旧翻译副本的内核或 SMMU 上发生。为了高效地实现这一点，架构允许 TLB 失效操作被广播到内部或外部可共享域。

给定的工作负载（如应用程序或虚拟机）可能只在一组已知的内核子集上运行。TLBI 域允许软件进一步微调 TLB 失效被广播到哪里。系统设计者可以将系统划分为一组域。当执行 TLBI 操作时，软件指定操作应广播到哪个域。这意味着只有该域的一部分内核会收到 TLB 失效操作。TLBI 域的数量和组成由系统设计者决定，通常可以通过固件表发现。

例如，下面是一个由四个 chiplet 组成的系统，每个 chiplet 包含 64 个内核。

![图 8-3：显示四个 chiplet 系统的图](../../asset/figure8-3-four-chiplets.png)

*图 8-3：显示四个 chiplet 系统的图*

该系统被划分为一组域：

- 域 0：在所有系统上，域 0 表示内部可共享域中的所有内核。
- 域 1 到 4：每个 chiplet 一个域。
- 域 8、9、10 和 11：一组对 chiplet 进行分组的域。

以上只是一个例子。然而，在这个例子中，软件可以选择将失效更精确地瞄准受影响工作负载运行过的地方。这种细粒度瞄准可以减少 TLB 失效操作的成本和延迟。

> 在某些情况下，为了能够使用 TLBI 域，软件必须使用操作的 TLBIP 变体。有关更多信息，请参见《Arm Architecture Reference Manual》中的各个指令描述。

## 9. 连续映射

连续映射（contiguous mappings）使 MMU 能够将一组相邻的页或块描述符表示为翻译阶段的单个连续区域。实现可以使用更少的翻译后备缓冲器（TLB）项来缓存该组，有时甚至减少到单个 TLB 项。这可以提高该范围的 TLB 效率。

连续映射给内核在翻译表的每一级提供了一种额外的映射大小。这些大小可以在软件映射内存时提供更多的灵活性，并可以减少翻译开销。然而，较大的连续映射如果覆盖了软件不需要映射的内存，可能会浪费内存。选择取决于内存映射需求。较大的映射可以提高 TLB 效率，而较小的映射提供对内存分配更细的控制。

### 9.1 Contiguous 位

要启用连续映射，软件在连续映射组中的每个块或页描述符中将 Contiguous 位设置为 1。Contiguous 位是对 MMU 的提示。实现不要求将该组缓存为单个 TLB 项。Contiguous 位在 Armv8-A 中引入。

软件在创建组时必须维护以下约束：

- 组中的每个相邻表项必须将 Contiguous 位设置为 1。
- 输入地址（IA）范围和输出地址（OA）范围都必须与连续映射的总大小对齐。
- 组中的每个相邻表项必须描述同一连续 OA 范围的一个不同的相邻块大小或页大小部分。
- 组中的每个相邻表项必须使用一致的属性和权限。
- 表项组作为整体必须在翻译表中与组中描述符的总字节大小对齐。

> 如果软件不满足这些约束，连续映射就是错误编程的。错误编程的连续映射可能导致 TLB 冲突中止或翻译结果不一致。

### 9.2 FEAT_CCONT

Linux folios 表明，对物理连续内存进行分组可以提高性能。Folios 简化了内核内存管理，并可以提高 TLB 效率。然而，到目前为止我们介绍的、在 Armv8-A 中引入的连续提示只支持固定的连续区域大小。固定的连续区域大小限制了操作系统内核在不浪费内存的情况下使用连续映射的频率。

FEAT_CCONT（可配置连续区域大小）是一个架构特性。FEAT_CCONT 使监管软件（包括 Linux）能够配置 MMU 使用更广泛的连续区域大小。Linux 内核可以使用这些大小在页表项中描述常见的连续物理内存范围。这些大小可以提高翻译延迟和 TLB 效率，同时限制内存浪费。FEAT_CCONT 还使软件能够动态改变区域的连续大小，而不会导致 TLB 冲突中止。

> FEAT_CCONT 计划作为 Future Arm Technologies 的一部分发布。

**FEAT_CCONT 的使用**

软件可以通过读取寄存器 ID_AA64MMFR3_EL1.CCONT 来检查是否实现了 FEAT_CCONT。

为每个翻译机制的每个阶段引入了一个新的控制寄存器字段 `(V)TCR(2)_ELx.CC`。术语 `(V)TCR(2)_ELx.CC` 表示以下所有：

- TCR2_EL1.CC。
- 如果实现了 EL2，TCR2_EL2.CC 和 VTCR_EL2.CC。
- 如果实现了 EL3，TCR_EL3.CC。

为简单起见，本节使用术语 CC 来指代相关的 `(V)TCR(2)_ELx.CC` 字段。为了进一步澄清，之前在 Armv8-A 中引入的、在前一章中介绍的连续提示现在将被称为“固定大小连续映射”。

当 CC 设置为 0 时，适用固定大小连续映射的行为。当 CC 设置为 1 时，Contiguous 位的含义被改变，这样组中的表项数量不再由固定数量的相邻块或页表项决定，而是从描述符中 OA 字段的最低有效位推导出来。

连续区域由硬件自然对齐。因此，对于一组相邻描述符的连续组，软件应将每个描述符的 OA 字段编程为相同的值，而不是像 CC 为 0 时那样递增。

当 CC 为 1 时，上表所示的相应位决定连续区域的大小。从最低有效位开始、在第一个为 0 的位处停止，计数切片中为 1 的位的数量 n。如果切片的所有位都是 1，则切片最高有效位被视为 0。连续区域的大小是块或页描述符在页表遍历级别所描述大小的 2^(n+1) 倍。

下图说明了连续区域大小（n）位是如何定位和计数的。

连续区域在 IA 空间和 OA 空间中对齐到其总大小。遍历级别 L 处连续区域的最大大小是级别 L-1 处块映射大小的一半。

例如，给定 4KB 颗粒，在第 3 级页表，对于 VMSAv8-64，且 n = 0：

```
2^(n+1) x (页/块大小) = 连续区域大小
2^(2+1) x 4KB = 连续区域大小
32KB = 连续区域大小
```

**性能指南**

映射大小是平均翻译延迟和内存分配粒度之间的权衡。较大的映射大小减少平均翻译延迟，而较小的映射大小通过提供更细的分配粒度来减少内存浪费。为了帮助软件选择高效的映射大小，实现可以在寄存器 CCONTIDR_EL1 中公布首选的连续区域大小。首选大小比非首选大小在翻译延迟和内存使用之间提供更好的平衡。然而，无论首选大小如何，较大的映射大小总是提供小于或等于较小映射大小的平均翻译延迟。

进一步演示：

```
首选大小：{ 32KB, 64KB, 128KB }
latency(128) <= latency(64) <= latency(32)
latency(512) <= latency(128)
```

## 10. 地址翻译指令

地址翻译（AT）指令让软件查询特定地址的翻译。产生的翻译（包括属性）被写入物理地址寄存器 PAR_EL1。

AT 指令的语法让你指定使用哪个翻译机制。例如，EL2 可以查询 EL0/EL1 翻译机制。然而，EL1 不能使用 AT 指令查询 EL2 翻译机制，因为这是特权的侵犯。

如果请求的翻译会导致故障，不会生成异常。相反，本会生成的故障类型被记录在 PAR_EL1 中。

## 11. 知识自测

**问：地址翻译中的阶段（stage）和级别（level）有什么区别？**

答：阶段是将输入地址翻译为输出地址的过程。对于 Stage 1，这是从 VA 到 IPA 的过程，对于 Stage 2，是从 IPA 到 PA 的过程。

级别指的是给定翻译阶段中的表。它也是较大的块如何细分为较小的块的方式。

**问：物理地址的最大大小是多少？**

答：物理地址空间的最大大小是实现定义的，最高 52 位（自 Armv8.2-A 起）。

**问：哪个寄存器字段控制虚拟地址空间的大小？**

答：TCR_ELx.TnSZ，或用于 Stage 2 的 VTCR_EL2.T0SZ。

**问：什么是翻译颗粒，支持的大小有哪些？**

答：它是可以描述的最小内存块。支持的大小是 4KB、16KB 和 64KB。

**问：TLBI ALLE3 做什么？**

答：它使 EL3 虚拟地址空间的所有 TLB 项失效。

**问：导致翻译故障的翻译表项可以被缓存在 TLB 中吗？**

答：不能，它不能被存储在 TLB 中。

**问：当 MMU 禁用时，地址是如何映射的？**

答：地址被平坦映射，因此输入和输出地址相同。

**问：什么是 ASID，TLB 项何时包含 ASID？**

答：ASID 是地址空间标识符，它标识翻译与哪个应用程序相关联。非全局映射（nG=1）在 TLB 中用 ASID 标记。
