## 1. 概述

指令集架构（Instruction Set Architecture，ISA）是计算机抽象模型的一部分。它定义了软件如何控制处理器。

Arm ISA 允许你编写符合 Arm 规格说明的软件和固件。这意味着，如果你的软件或固件符合这些规格说明，那么任何基于 Arm 的处理器都会以相同的方式执行它。

本指南介绍 A64 指令集，该指令集用于 64 位 Armv8-A 架构，也被称为 AArch64。

本指南不会涵盖每一条指令。所有指令在《Arm Architecture Reference Manual》中都有详细说明。取而代之的是，我们将介绍指令的格式、不同类型的指令，以及用汇编语言编写的代码如何与编译器生成的代码进行交互。

在本指南末尾，你可以进行“知识自测”。你将学习指令的主要类别、数据处理指令的语法，以及 W 和 X 寄存器的使用如何影响指令。我们希望你能从本指南中学到的关键成果是：当给定一个 C 程序及其编译器输出时，能够解释生成的汇编代码如何映射到 C 语句。最后，本指南将向你展示如何用汇编语言编写一个可以被 C 调用的函数。

## 2. 为什么你应该关心 ISA

作为开发者，你在日常工作中可能不需要直接编写汇编代码。然而，汇编代码在某些领域仍然很重要，例如第一阶段启动软件（first stage boot software）或某些低层内核活动。

即使你不直接编写汇编代码，理解指令集能做什么、以及编译器如何利用这些指令，也能帮助你编写更高效的代码。它还能帮助你理解编译器的输出。这在调试时会很有用。

## 3. Arm 架构中的指令集

Armv8-A 支持三种指令集：A32、T32 和 A64。

A64 指令集在 AArch64 执行状态下执行时使用。它是一种定长 32 位指令集。名称中的“64”指的是该指令由 AArch64 执行状态使用，而不是指指令在内存中的大小。

A32 和 T32 指令集也分别被称为 Arm 和 Thumb。这些指令集在 AArch32 执行状态下执行时使用。在本指南中，我们不涵盖 A32 和 T32 指令集。要了解更多关于这些指令集的信息，请参见“相关资料”。

## 4. 指令集资源

每个版本的 Arm 架构都有各自的《Arm Architecture Reference Manual》，可以在 Arm Developer 网站上找到。每份 Arm ARM 都提供了每条指令的详细描述，包括：

- 编码（Encoding）——指令在内存中的表示。
- 参数（Arguments）——指令的输入。
- 伪代码（Pseudocode）——指令做什么，用 Arm 伪代码语言表达。
- 限制（Restrictions）——指令何时不能使用，或它可能触发的异常。

A64 的指令描述也有 XML 和 HTML 格式。如果你需要经常查阅指令，XML 和 HTML 格式会很有用。XML 和 HTML 格式可以在 Arm Developer 网站上找到，你可以在“相关资料”中找到链接。XML 可以作为压缩归档下载，HTML 可以使用网络浏览器查看和搜索。

> XML/HTML 中的信息与《Arm Architecture Reference Manual》中的信息来自同一来源，但格式可能略有不同。

## 5. 简单顺序执行

Arm 架构按照简单顺序执行（Simple Sequential Execution，SSE）模型描述指令。这意味着处理器表现得如同一次只取指、译码并执行一条指令，并且按照指令在内存中出现的顺序进行。

实际上，现代处理器拥有可以同时执行多条指令的流水线，并且可能乱序执行。下图展示了一个 Arm Cortex 处理器的流水线示例：

![图 5-1：Cortex 流水线示例](../../asset/figure5-1-example-cortex-pipeline.png)

*图 5-1：Cortex 流水线示例*

你会记得，架构是一种功能描述。这意味着它不规定单个处理器如何工作。每个处理器即使在内部对指令进行重排序，也必须与简单顺序执行模型保持一致的行为。

## 6. AArch64 中的寄存器 —— 通用寄存器

大多数 A64 指令对寄存器进行操作。架构提供了 31 个通用寄存器。每个寄存器都可以用作 64 位 X 寄存器（X0..X30），或用作 32 位 W 寄存器（W0..W30）。这是查看同一个寄存器的两种不同方式。例如，下面的寄存器图显示 W0 是 X0 的低 32 位，W1 是 X1 的低 32 位：

![图 6-1：寄存器图](../../asset/figure6-1-register-diagram.png)

*图 6-1：寄存器图*

对于数据处理指令，选择 X 还是 W 决定了操作的大小。使用 X 寄存器将产生 64 位计算，使用 W 寄存器将产生 32 位计算。下面的例子执行 32 位整数加法：

```asm
ADD W0, W1, W2
```

下面的例子执行 64 位整数加法：

```asm
ADD X0, X1, X2
```

如上面的例子所示，当一个 W 寄存器被写入时，64 位寄存器的上 32 位会被清零。

还有一组单独的 32 个寄存器用于浮点和向量操作。这些寄存器是 128 位的，但与通用寄存器一样，可以通过多种方式访问。Bx 为 8 位，Hx 为 16 位，依此类推，直到 Qx 为 128 位。

![图 6-2：寄存器图](../../asset/figure6-2-register-diagram.png)

*图 6-2：寄存器图*

你为寄存器使用的名称决定了计算的大小。下面的例子执行 32 位浮点加法：

```asm
FADD S0, S1, S2
```

下面的例子执行 64 位浮点加法：

```asm
FADD D0, D1, D2
```

这些寄存器也可以被称为 V 寄存器。当使用 V 形式时，寄存器被视为一个向量。这意味着它被视为包含多个独立的值，而不是单个值。下面的例子执行向量浮点加法：

```asm
FADD V0.2D, V1.2D, V2.2D
```

下面的例子执行向量整数加法：

```asm
ADD  V0.2D, V1.2D, V2.2D
```

我们将在本指南后面更详细地介绍向量指令。

## 7. AArch64 中的寄存器 —— 其他寄存器

以下是 A64 中你应该了解的另外一些寄存器：

- **零寄存器** XZR 和 WZR，读取时总是为 0，并忽略写入。
- 你可以将 **栈指针（SP）** 用作加载和存储的基址。你也可以将栈指针用于有限的一组数据处理指令，但它不是普通的通用寄存器。Armv8-A 有多个栈指针，每个栈指针都与特定的异常级别相关联。当指令中使用 SP 时，它表示当前的栈指针。异常模型指南解释了栈指针是如何被选择的。
- **X30** 被用作链接寄存器（Link Register），可以被称为 LR。另有单独的寄存器 ELR_ELx 用于从异常返回。这在异常模型指南中有更详细的讨论。
- **程序计数器（PC）** 在 A64 中不是通用寄存器，不能与数据处理指令一起使用。PC 可以使用以下指令读取：

```asm
ADR Xd, .
```

ADR 指令返回一个标签的地址，基于当前位置计算得出。点号（.）表示“这里”，所以上面所示指令返回的是它自身的地址。这等效于读取 PC。一些分支指令以及一些加载/存储操作会隐式地使用 PC 的值。

> 在 A32 和 T32 指令集中，PC 和 SP 是通用寄存器。在 A64 指令集中则不是这样。

## 8. AArch64 中的寄存器 —— 系统寄存器

除了通用寄存器之外，架构还定义了系统寄存器。系统寄存器用于配置处理器，以及控制诸如 MMU 和异常处理之类的系统。

系统寄存器不能直接用于数据处理或加载/存储指令。相反，需要将系统寄存器的内容读入 X 寄存器，进行操作，然后再写回系统寄存器。访问系统寄存器有两个专用指令：

```asm
MRS        Xd, <system register>
```

将系统寄存器读入 Xd。

```asm
MSR        <system register>, Xn
```

将 Xn 写入系统寄存器。

系统寄存器按名称指定，例如 SCTLR_EL1：

```asm
MRS        X0, SCTLR_EL1
```

将 SCTLR_EL1 读入 X0。

系统寄存器名称以 `_ELx` 结尾。`_ELx` 指定访问该寄存器所需的最低特权。例如：

- `SCTLR_EL1`：需要 EL1 或更高特权。
- `SCTLR_EL2`：需要 EL2 或更高特权。
- `SCTLR_EL3`：需要 EL3 特权。

以不足的特权访问寄存器会导致异常。

有时你会看到 `_EL12` 或 `_EL01`。这些用于虚拟化。请参阅虚拟化指南了解更多信息。

## 9. 数据处理 —— 算术和逻辑运算

逻辑和整数算术指令的基本格式为：

![图 9-1：逻辑和整数算术指令格式](../../asset/figure9-1-instr-format.png)

*图 9-1：逻辑和整数算术指令格式*

指令的各部分如下：

- **操作（Operation）**定义了指令做什么。例如，ADD 做加法，AND 执行逻辑与。可以在操作后面加一个 S 来设置标志。例如，ADD 变成 ADDS。这个 S 告诉处理器根据指令的结果更新 ALU 标志。我们将在“生成条件码”一节讨论 ALU 标志。
- **目标（Destination）**是指令的目标，总是一个寄存器，指定操作结果放置的位置。大多数指令只有一个目标寄存器。少数指令有两个目标寄存器。当目标是 W 寄存器时，对应 X 寄存器的上 32 位被设置为 0。
- **操作数 1（Operand 1）**始终是一个寄存器。这是指令的第一个输入。
- **操作数 2（Operand 2）**是一个寄存器或一个常量，是指令的第二个输入。当操作数 2 是寄存器时，它可以包含一个可选的移位。当操作数 2 是常量时，它被编码在指令本身内部。这意味着可用的常量范围是有限的。

你应该注意几个特殊情况，例如 MOV 和 MVN 指令。MOV 将一个常量、或另一个寄存器的内容，移入指定为目标的寄存器。

MOV 和 MVN 只需要一个输入操作数，它可以是寄存器或常量，如下所示：

```asm
MOV       X0, #1
```

设置：X0 = 1

```asm
MVN       W0, W1
```

设置：W0 = ~W1

## 10. 数据处理 —— 浮点

浮点操作遵循与整数数据处理指令相同的格式，并使用浮点寄存器。与整数数据处理指令一样，操作的大小决定了所用寄存器的大小。浮点指令的操作部分总是以 F 开头。例如，这条指令以半精度设置 H0 = H1 / H2：

```asm
FDIV       H0, H1, H2
```

这条指令以单精度设置 S0 = S1 + S2：

```asm
FADD       S0, S1, S2
```

这条指令以双精度设置 D0 = D1 - D2：

```asm
FSUB       D0, D1, D2
```

### 10.1 8 位和 16 位浮点的支持

Arm 架构包含对 16 位和 8 位浮点格式的支持。

![图 10-1：数据格式之间的差异](../../asset/figure10-1-data-formats.png)

*图 10-1：数据格式之间的差异*

Armv8.2-A 增加了对 16 位浮点 FP16（FEAT_FP16）的支持。对 FP16 的支持从 Armv8.2-A 起是可选的，如果实现了 SVE 或 SVE2 则变为强制，这意味着它在 Armv9-A 中实际上是强制的。

BFloat16（通常缩写为 BF16）是一种替代的 16 位浮点存储格式。BF16 从 Armv8.2-A（FEAT_BF16）起可选支持，但在 Armv8.6-A 和 Armv9.1-A 中变为强制。BF16 是最近出现的一种专为神经网络（NN）高性能处理而量身定制的格式。

FP16 和 BF16 格式之间的区别在于指数和尾数之间如何分配位，如上面的图所示。BF16 的指数范围与 FP32 相同，但尾数的位数较少。这使得 BF16 与 FP32 之间的转换更简单，因为 BF16 实际上是 FP32 的较低精度版本。

有关 BF16 的更多信息，请参见博客《AWS Graviton3 featuring Arm Neoverse V1 is up to 1.8x faster than x86 for deep learning inference workloads》。

2022 年，Arm、Intel 和 Nvidia 宣布合作开发 FP8，这是一种交换格式，使软件生态系统能够轻松共享 NN 模型，并支持 AI 计算能力的持续进步。这成为了 OCP8 标准，支持于 Armv9.2-A（FEAT_FP8、FEAT_FP8xxx）中被引入架构。

FP8 引入了一对格式：E5M2 和 E4M3。这两种格式在精度和范围之间提供了不同的权衡。

使用 FP8 时，使用哪种格式（E5M2 还是 E4M3）由 FPMR 寄存器中的字段选择。可以为指令的不同输入选择不同的格式，从而高效地处理不同格式的数据集。

为了支持其他小尺寸数据格式，Armv9.6-A 和 Armv9.7-A 引入了查找表（LUT）指令（FEAT_LUT、SVE2.3 和 SME2.3）。这些指令允许软件高效地将 2 位、4 位或 6 位格式转换为其他格式进行处理。

### 10.2 浮点支持是可选的吗？

不是。在 Armv8-A 中，对浮点的支持是强制的。架构规定，只要使用像 Linux 这样的富操作系统，就需要它。

从技术上讲，如果你运行的是一个完全专有的软件栈，你可以省略浮点支持。但大多数工具链，包括 GCC 和 Arm Compiler 6，都会假设存在浮点支持。

## 12. 数据处理 —— 扩展与饱和

有时需要将数据从一种大小转换为另一种大小。SXTx（符号扩展）和 UXTx（无符号扩展）指令可用于这种转换。在这种转换中，x 决定被扩展数据的大小，如下图所示：

![图 12-1：数据大小转换示例](../../asset/figure12-1-data-size-conversion.png)

*图 12-1：数据大小转换示例*

在第一条指令 SXTB 中，B 表示字节（byte）。它取出 W0 的低字节并将其符号扩展到 32 位。

UXTH 是半字（H）的无符号扩展。它取出 W1 的低 16 位并将其零扩展到 32 位。

前两个示例以 W 寄存器作为目标，意味着扩展是到 32 位。第三个示例以 X 寄存器作为目标，意味着符号扩展是到 64 位。

### 12.1 自测

编写一条指令，将 W5 中的一个字节符号扩展到 64 位，结果放入 X7。

```asm
SXTB X7, W5
```

### 12.2 子寄存器大小的整数数据处理

有些指令执行饱和算术（saturating arithmetic）。这意味着如果结果大于或小于目标所能容纳的范围，那么结果会被设置为目标整数范围的最大值或最小值。

数据处理指令可以高效地处理 32 位数据和 64 位数据。在实践中，你在处理子寄存器计算时经常看到饱和指令。子寄存器计算是 16 位或 8 位的计算。以下示例展示了 C 语言中的子寄存器计算及其生成的汇编代码。

**示例 1**

C 代码：

```c
uint32_t add32(uint32_t a, uint32_t b) {
    return a+b;
}
```

生成的汇编：

```asm
add32:
  ADD  W0, W1, W0
  RET
```

**示例 2**

C 代码：

```c
uint16_t uadd16(uint16_t a, uint16_t b) {
  return a+b;
}
```

生成的汇编：

```asm
uadd16:
  AND  W8, W1, #0xffff
  ADD  W0, W8, W0, UXTH
  RET
```

**示例 3**

C 代码：

```c
int16_t sadd16(int16_t a, int16_t b) {
  return a+b;
}
```

生成的汇编：

```asm
sadd16:
  SXTH  W8, W1
  ADD   W0, W8, W0, SXTH
  RET
```

在第一个示例中，32 位加法映射到 W 寄存器上，因此可以轻松处理。对于 16 位示例，需要一条额外的指令。第三个示例取出 16 位输入，将它们扩展到 32 位，然后执行加法。该序列使用以下指令将 16 位输入转换为 32 位：

```asm
SXTH  W8, W1
```

然后，这条指令执行加法并将结果饱和到有符号 16 位：

```asm
ADD   W0, W8, W0, SXTH
```

在 ADD 操作的操作数列表末尾加上 `, SXTH`，会使结果使用饱和算术。因为目标是 W 寄存器，所以 ADD 指令饱和到 16 位整数范围。

## 13. 数据处理 —— 格式转换

我们已经看到 MOV 和 MVN 指令将值从一个寄存器复制到另一个寄存器。类似地，FMOV 可用于在浮点寄存器和通用寄存器之间复制。

然而，使用 FMOV 复制的是寄存器之间的字面位模式。还有一些指令可以转换为最接近的表示，如下图所示：

![图 13-1：FMOV/SCVTF 示例](../../asset/figure13-1-fmov-scvtf-example.png)

*图 13-1：FMOV/SCVTF 示例（原图题注为 "EMOV example"）*

在这个例子中，假设 X0 包含值 2（正整数 2）：

```
X0 = 0x0000_0000_0000_0002
```

然后执行以下序列：

```asm
FMOV D0, X0
SCVTF D1, X0
```

两条指令都将 X0“复制”到一个 D 寄存器。然而，结果却大不相同：

```
D0 = 0x0000_0000_0000_0002 = 9.88131e-324
D1 = 0x4000_0000_0000_0002 = 2.0
```

FMOV 复制了字面位模式，将其解释为浮点值时是一个截然不同的值。SCVTF 则将 X0 中的值转换为浮点中最接近的等效值。

类似地，FCVTxx 可用于将浮点值转换为其最接近的整数表示。在这种情况下，xx 的不同取值控制所使用的舍入模式。

## 14. 数据处理 —— 向量和矩阵数据

A64 架构还提供了对向量数据处理的支持。可用的两种向量处理类型是：

- 高级 SIMD（Advanced SIMD），也被称为 NEON。
- 可扩展向量扩展（Scalable Vector Extension，SVE 和 SVE2）。SVE 在 Armv8-A 中引入，针对 HPC 工作负载进行了优化。Armv9-A 引入了 SVE2，它扩展了基础 SVE 以支持更多使用场景。

![图 14-1：SVE 和 SVE2](../../asset/figure14-1-sve-sve2.png)

*图 14-1：SVE 和 SVE2*

我们将在稍后的向量编程指南中介绍这两种向量处理类型。

> 名称“Advanced SIMD”源于 Armv6 中存在的、对普通 32 位通用寄存器进行操作的 SIMD 指令。在 Armv7 中，术语“Advanced SIMD”用于可以对 128 位向量进行操作的指令。Armv6 风格的指令在 A64 中不存在，但命名约定保留了下来。

Armv9-A 还引入了可选的可扩展矩阵扩展（SME 和 SME2）。SME 构建在 SVE2 之上，增加了高效处理矩阵的新能力。关键特性包括：

- 矩阵瓦片（tile）存储
- 加载、存储、插入和提取瓦片向量，包括即时转置
- SVE 向量的外积
- 流式 SVE 模式

SME 提供外积指令来加速矩阵操作。SME2 通过多向量操作、多向量谓词、范围预取和 2b/4b 权重压缩等指令显著扩展了能力。

![图 14-2：SME 和 SME2](../../asset/figure14-2-sme-sme2.png)

*图 14-2：SME 和 SME2*

这些新指令使 SME2 能够比最初的 SME 加速更多工作负载，包括 GEMV、非线性求解器、小型稀疏矩阵，以及特征提取或跟踪。

## 15. 加载与存储

基本的加载和存储操作是：LDR（加载）和 STR（存储）。这些操作在内存和通用寄存器之间传输单个值。这些指令的语法为：

```
LDR<Sign><Size>   <Destination>, [<address>]
STR<Size>         <Source>, [<address>]
```

## 16. 加载与存储 —— 大小

加载或存储的大小由寄存器类型 X 或 W 以及 Size 字段决定。X 用于 64 位，W 用于 32 位。例如，这条指令将 32 位从地址加载到 W0：

```asm
LDR        W0, [<address>]
```

这条指令将 64 位从地址加载到 X0：

```asm
LDR        X0, [<address>]
```

Size 字段允许你加载子寄存器大小的数据量。例如，这条指令将 W0 的低字节（B）存储到地址：

```asm
STRB       W0, [<address>]
```

这条指令将 W0 的低半字（H）存储到地址：

```asm
STRH       W0, [<address>]
```

最后，这条指令将 X0 的低字（W）存储到地址：

```asm
STRW       X0, [<address>]
```

### 17.1 任务

如果地址 0x8000 处的字节包含值 0x1F，那么 LDRSB X4 的结果是什么？

LDRSB 执行的是带符号扩展到 64 位的字节加载。所加载值的最高有效位将被复制以填满 64 位寄存器。所加载的值 0x1F 的最高位是清除的。因此，X4 中的值将是 0x0000_0000_0000_001F。

## 19. 加载与存储 —— 加载对与存储对

到目前为止，我们讨论了单个寄存器的加载和存储。A64 还有加载对（LDP）和存储对（STP）指令。

这些指令在内存和两个寄存器之间传输数据。寄存器按操作数顺序从左到右处理。也就是说，第一个寄存器操作数从第一个地址加载、或存储到第一个地址。第二个寄存器操作数从下一个连续地址加载、或存储到下一个连续地址。

考虑以下示例。

第一条指令将 [X0] 加载到 W3，并将 [X0 + 4] 加载到 W7：

```asm
LDP        W3, W7, [X0]
```

第二条指令将 D0 存储到 [X4]，并将 D1 存储到 [X4 + 8]：

```asm
STP        D0, D1, [X4]
```

加载对和存储对指令常用于压栈和出栈。第一条指令将 X0 和 X1 压入栈：

```asm
STP        X0, X1, [SP, #-16]!
```

第二条指令将 X0 和 X1 从栈中弹出：

```asm
LDP        X0, X1, [SP], #16
```

请记住，在 AArch64 中，栈指针必须是 128 位对齐的。

**排序、对齐与原子性**

加载对和存储对指令被视为执行两次独立的访问。架构不保证访问执行的顺序。如果访问的顺序很重要，那么加载对或存储对指令就不适用。

对齐要求基于访问大小，而不是总大小。例如：

```asm
LDP W3, W7, [X0]
```

这条指令被视为执行两次 32 位访问。因此，要对齐，地址必须是 4 字节对齐的，即使所加载的总字节数是 8。

如果目标地址是对齐的，那么加载对或存储对指令执行的每次访问都是单副本原子（single-copy atomic）的。

如果实现了 FEAT_LSE2，那么在某些情况下，整个操作可以是单副本原子的。

**对 MMIO 使用加载对或存储对指令**

加载对和存储对指令通常不适合与 MMIO 寄存器交互。系统软件程序员在访问 MMIO 寄存器时，不应使用加载对或存储对指令，也不应让编译器生成它们。

MMIO 设备寄存器通常只支持有限的一组访问大小。一个常见的要求是，对 MMIO 寄存器的访问是寄存器大小的、对齐的并且单副本原子的。例如，大多数通用中断控制器第 3 版（GICv3）的 MMIO 寄存器是 32 位的，只支持 32 位对齐的访问。

与内存映射设备寄存器交互时，访问的顺序通常也很重要。

对 MMIO 设备寄存器使用加载对或存储对指令可能导致意想不到且不受欢迎的结果。例如，使用 LDP 指令访问两个相邻的寄存器可能导致访问顺序不符合预期。类似地，如果使用带 W 寄存器的 LDP 访问单个 64 位寄存器，这可能表现为对设备的两次访问，而设备可能不支持。

对 MMIO 使用成对指令的另一个考虑是故障行为。当加载对或存储对指令发生故障时，所提供的综合（syndrome）信息可能不足以可靠地重建指令的两个部分中哪个导致了故障。

## 20. 加载与存储 —— 使用浮点寄存器

加载和存储也可以使用浮点寄存器进行，正如我们在这里将看到的。第一条指令将 64 位从 [X0] 加载到 D1：

```asm
LDR        D1, [X0]
```

第二条指令将 128 位从 Q0 存储到 [X0 + X1]：

```asm
STR        Q0, [X0, X1]
```

最后，这条指令从 X5 加载一对 128 位值，然后将 X5 增加 256：

```asm
LDP        Q1, Q3, [X5], #256
```

有一些限制：

- 大小仅由寄存器类型指定。
- 没有对加载进行符号扩展的选项。
- 地址仍然必须是 X 寄存器。

使用浮点寄存器的加载和存储可以在意想不到的场景中出现。memcpy() 类型的例程使用它们是常见的。这是因为更宽的寄存器意味着需要更少的迭代次数。仅仅因为你的代码不使用浮点值，就不要假设你不需要使用浮点寄存器。

## 22. 程序流

通常，处理器按程序顺序执行指令。这意味着处理器按照指令在内存中设置的顺序执行它们。改变这种顺序的一种方式是使用分支指令。分支指令改变程序流，用于循环、判断和函数调用。

A64 指令集也有一些条件分支指令。这些指令根据先前指令的结果改变它们的执行方式。

> Armv8.3-A 和 Armv8.5-A 引入了指令来防护面向返回的编程（return-oriented programming）和面向跳转的编程（jump-oriented programming）。

## 23. 程序流 —— 循环与判断

在本节中，我们将研究循环和判断如何让你使用分支指令改变程序代码的流程。有两种类型的分支指令：无条件的和有条件的。

### 23.1 无条件分支指令

有两种类型的无条件分支指令；B 表示 Branch（分支），BR 表示 Branch with Register（寄存器分支）。

无条件分支指令 `B <label>` 执行到 `<label>` 的直接、PC 相对分支。从当前 PC 到目标的偏移被编码在指令内。范围受到指令内记录偏移的可用空间的限制，为 +/-128MB。

当你使用 `BR <Xn>` 时，BR 执行到 Xn 中指定地址的间接（或绝对）分支。

### 23.2 条件分支指令

条件分支指令 `B.<cond> <label>` 是 B 指令的条件版本。仅当条件 `<cond>` 为真时才进行分支。范围限制为 +/-1MB。

条件根据存储在 PSTATE 中的 ALU 标志进行测试，需要由先前指令（如比较 CMP）生成。

`CBZ <Xn> <label>` 和 `CBNZ <Xn> <label>`

此指令在 Xn 包含 0 时分支到 `<label>`（CBZ），在 Xn 不包含 0 时分支到 label（CBNZ）。

`TBZ <Xn>, #<imm>, <label>` 和 `TBNZ <Xn>, #<imm>, <label>`

TBZ 和 TBNZ 指令的工作方式与 CBZ 和 CBNZ 类似，但测试由 `<imm>` 指定的单个位，而不是整个寄存器值。

> 直接（或 PC 相对）分支将到目标的偏移存储在指令内。条件分支的范围较小。这是因为需要一些位来存储条件本身，从而留给偏移的位就少了。

将这些映射到你可能在 C 中编写的内容，以下示例展示了分支如何用于循环和判断。

考虑以下 C 代码：

```c
if (a == 5)
  b = 5;
```

编译器对上述 C 代码的典型输出可能如下：

```asm
   CMP W0, #5
   B.NE skip
   MOV W8, #5
skip:
```

考虑以下 C 代码：

```c
while (a != 0)
{
  b = b + c;
  a = a - 1;
}
```

编译器对上述 C 代码的典型输出可能如下：

```asm
loop:
  CBZ W8, skip
  ADD W9, W9, W10
  SUB W8, W8, #1
  B loop
skip:
```

> 输出中显示的标签不是由编译器创建的。这里包含它们是为了便于阅读。

### 23.3 自测

A64 中没有条件间接分支指令。如果 X5 包含 0，你如何构造一个执行到 X1 中地址的绝对分支的指令序列？

没有唯一正确的答案，但类似这样的序列是可以接受的：

```asm
  CMP      X5, XZR     // 将 X5 与零比较
  B.NE skip            // 如果 X5!=0 则跳过 BR
  BR    X1
skip:
...
```

## 24. 程序流 —— 生成条件码

在“程序流 - 循环与判断”中，我们了解到 `<cond>` 是根据存储在 PSTATE 中的 ALU 标志进行测试的。

ALU 标志作为数据处理指令的副作用被设置。回顾一下，操作末尾的 S 会导致 ALU 标志被更新。这是一个 ALU 标志不被更新的指令示例：

```asm
ADD        X0, X1, X2
```

这是一个使用 S 更新 ALU 标志的指令示例：

```asm
ADDS       X0, X1, X2
```

这种方法允许软件控制何时更新或不更新标志。标志可以被后续的条件指令使用。以下面的代码为例：

```asm
SUBS       X0, X5, #1
AND     X1, X7, X9
B.EQ    label
```

SUBS 指令执行减法并更新 ALU 标志。然后 AND 指令执行与操作，并且不更新 ALU 标志。最后，B.EQ 指令执行条件分支，使用减法结果设置的标志。

标志是：

- N —— 负（Negative）
- C —— 进位（Carry）
- V —— 溢出（Overflow）
- Z —— 零（Zero）

以 Z 标志为例。如果操作结果为零，那么 Z 标志被设置为 1。例如，这里如果 X5 为 1，Z 标志将被设置，否则它将被清除：

```asm
SUBS       X0, X5, #1
```

条件码映射到这些标志，并且成对出现。以 EQ（相等）和 NE（不相等）为例，看看它们如何映射到 Z 标志：

EQ 码检查 Z==1。NE 码检查 Z==0。

以下面的代码为例：

```asm
SUBS       W0, W7, W9            // W0 = W7 - W9
B.EQ    label
```

在第一行，我们有一个减法操作。因为我们使用了 S 后缀，如果结果为零，这个减法操作会设置 Z 标志。在最后一行，如果 Z==1 则分支到 label。

如果 w7==w9，减法的结果将为零，Z 标志将被设置。因此，如果 w7 和 w9 相等，将进行到 label 的分支。

除了常规的数据处理指令，还有其他只更新 ALU 标志的指令：

- CMP —— 比较（Compare）
- TST —— 测试（Test）

这些指令是其他指令的别名。例如：

```asm
CMP X0, X7     // 是 SUBS XZR, X0, X7 的别名
TST W5, #1     // 是 ANDS WZR, W5, #1 的别名
```

通过使用零寄存器作为目标，我们丢弃了操作的结果，只更新 ALU 标志。

### 24.1 自测

到目前为止我们看到的示例使用了 EQ 和 NE 条件。编写一个序列，如果 (X5 - X6) 的结果为负，则将 X0 设置为 5。为此，你需要在《Arm Architecture Reference Manual》中查找完整的条件码列表。

你可以编写多个序列。这里有一个例子：

```asm
SUBS       XZR, X5, X6
B.PL    1a        // 结果为正或零则分支
MOV     X0, #5    // 仅在结果为负时执行
1:
...
```

在这里使用条件选择指令可能是更好的选择。

## 25. 程序流 —— 条件选择指令

到目前为止，我们已经看到了使用分支来处理判断的示例。A64 指令集还提供了条件选择指令。在许多情况下，这些指令可以作为分支的替代方案。

有许多变体，但基本形式是：

```asm
CSEL       Xd, Xn, Xm, cond
```

这意味着：

```text
if cond then
  Xd = Xn
else
  Xd = Xm
```

你可以在以下代码中看到一个示例：

```asm
CMP        W1, #0
CSEL    W5, W6, W7, EQ
```

它给出的结果与以下相同：

```text
if (W1==0) then
  W5 = W6
else
  W5 = W7
```

有些变体将另一种操作与条件选择结合起来。例如，CSINC 执行选择和加一：

```asm
CSINC      Xd, Xn, Xm, cond
```

这意味着：

```text
if cond then
  Xd = Xn
else
  Xd = Xm + 1
```

要仅条件递增，你可以写：

```asm
CSINC        X0, X0, X0, cond
```

它等同于：

```text
if cond then
  X0 = X0
else
  X0 = X0 + 1
```

架构为这个命令提供了一个别名 CINC。不过请注意，CINC 反转了 CSINC 的逻辑：

- `CSINC X0, X0, X0, cond` 在 cond 为真时保持 X0 不变，在 cond 为假时递增 X0
- `CINC X0, X0, cond` 在 cond 为真时递增 X0，在 cond 为假时保持 X0 不变

编译器会选择最有效的方法来实现程序中的功能。对于执行简单操作的小型 if ... else 语句，编译器通常使用条件选择，因为条件选择可能比分支更高效。

以下是一些简单的 if ... else 示例，将使用分支的实现与使用条件选择指令的等效实现进行比较：

| C 代码 | 使用分支 | 使用条件选择 |
| --- | --- | --- |
| `if (a != 0) b = b + 1;` | `CMP W0, #0` `B.EQ else` `ADD W1, W1, #1` `else: ...` | `CMP W0, #0` `CINC W1, W1, NE` |
| `if (a == 0) y = y + 1; else y = y - 1;` | `CMP W0, #0` `B.NE else` `ADD W1, W1, #1` `B end` `else: SUB W1, W1, #1` `end: ...` | `CMP W0, #0` `SUB W2, W1, #1` `CSINC W1, W2, W1, NE` |

在这些类型的示例中，条件选择有一些优势。序列更短，并且无论结果如何都占用相同数量的指令。

重要的是，条件选择还消除了分支的需要。在现代处理器中，这种分支可能难以被分支预测逻辑正确预测。错误预测的分支会对性能产生负面影响，因此最好尽可能移除分支。

## 26. 程序流 —— 条件故障指令

许多编程语言执行运行时一致性检查，例如边界检查。这些检查会生成许多条件分支到断点异常（BRK）或测试到 BRK 的序列。

到 BRK 的分支很少被采取，但分支指令增加了代码大小，并可能增加分支预测器的压力。为了减少代码开销，Armv9.8-A 引入了可选的条件故障指令扩展（FEAT_CFLT）。该特性提供了生成异常而不是分支的条件指令。异常根据条件标志的状态、或比较的结果来生成。条件故障异常被同步地送入。

在没有条件故障指令的情况下，一个典型的检查可能如下所示：

```asm
    cmp     x1, x10
    b.hs    .Lerror
    ldr     w0, [x9, x1, lsl #2]
    ret
.Lerror:
    brk     #0x1
```

在上面所示的代码示例中，检查使用了一条比较指令和一条到故障指令的条件分支。

使用条件故障指令，一个检查可以如下所示：

```asm
    cflths  #0, x1, x10
    ldr     w0, [x9, x1, lsl #2]
    ret
```

这条指令仅当比较条件为真时才使处理器进入异常状态。

FEAT_CFLT 定义了几组指令：

- **FLT.cond** 根据当前条件标志引起异常，与 B.cond 到 BRK 的序列最为接近。FLT.cond 有一个 16 位的 reason 字段，行为类似于条件超级用户调用：
  - 在 EL0 执行时，当 EL0 异常由 EL1 处理时，异常被送入 EL1；当 EL0 异常由 EL2 处理时，异常被送入 EL2。
  - 在 EL1、EL2 和 EL3 执行时，异常在当前异常级别被送入。
- **CFLT\<cc\>** 比较两个操作数，当比较为真时引起异常。它有两种形式。
  - 寄存器形式比较两个寄存器：

```asm
    cfltge  #reason, x0, x1     // 有符号比较，如果 x0 >= x1 则故障
```

  - 立即数形式比较一个寄存器与一个小立即数值：

```asm
    cfltge  #reason, x0, #10   // 有符号比较，如果 x0 >= #10 则故障
```

- **CFLTZ 和 CFLTNZ** 与零/非零比较：

```asm
    cfltz   #reason, x0     // 如果 x0 == 0 则故障
    cfltnz  #reason, x0     // 如果 x0 != 0 则故障
```

- **TFLTZ 和 TFLTNZ** 测试寄存器中的一位，并根据其值故障：

```asm
    tfltz   #reason, x0, #5     // 如果 x0 的第 5 位为 0 则故障
    tfltnz  #reason, x0, #5     // 如果 x0 的第 5 位为 1 则故障
```

每条指令都有一个 reason 字段。当条件故障异常发生时，reason 字段被复制到 ESR_ELx.ISS。异常处理器可以使用 reason 字段来区分少量的故障原因。如果软件需要更多的故障原因，它可以设置带普通比较或测试的标志，然后使用 FLT.cond 作为故障指令。

## 27. 函数调用

在调用函数或子例程时，我们需要一种方法在完成后返回到调用者。在 B 或 BR 指令后加一个 L 会将它们变成带链接的分支（branch with link）。这意味着作为分支的一部分，返回地址被写入 LR（X30）。

> 名称 LR 和 X30 是可以互换的。诸如 GNU GAS 或 armclang 之类的汇编器两者都接受。

有一个专门的函数返回指令 RET。它执行到链接寄存器中地址的间接分支。总之，我们得到：

![图 27-1：RET](../../asset/figure27-1-ret.png)

*图 27-1：RET*

上图展示了用 GAS 语法汇编编写的函数 foo()。关键字 `.global` 导出符号，`.type` 表示导出的符号是一个函数。

为什么我们需要专门的函数返回指令？从功能上讲，`BR LR` 与 RET 会做相同的事情。使用 RET 告诉处理器这是一次函数返回。大多数现代处理器以及所有 Cortex-A 处理器都支持分支预测。知道这是一次函数返回，可以让处理器更准确地预测分支。

分支预测器猜测程序流在分支之间将采取的方向。该猜测用于决定将什么加载到含有等待处理指令的流水线中。如果分支预测器猜对了，流水线中就有正确的指令，处理器就不必等待从内存加载指令。

## 28. 过程调用标准

Arm 架构对通用寄存器的使用几乎没有限制。回顾一下，整数寄存器和浮点寄存器是通用寄存器。然而，如果你想让你的代码与别人编写的代码、或与编译器生成的代码交互，那么你就需要就寄存器使用约定规则。对于 Arm 架构，这些规则被称为过程调用标准（Procedure Call Standard，PCS）。

PCS 规定了：

- 哪些寄存器用于将参数传入函数。
- 哪些寄存器用于将值返回给发起调用的函数（称为调用者 caller）。
- 被调用的函数（称为被调用者 callee）可以破坏哪些寄存器。
- 被调用者不能破坏哪些寄存器。

考虑一个从 main() 调用的函数 foo()：

![图 28-1：PCS 示例](../../asset/figure28-1-pcs-example.png)

*图 28-1：PCS 示例*

PCS 规定第一个参数在 X0 中传递，第二个参数在 X1 中传递，依此类推，直到 X7。任何进一步的参数都在栈上传递。我们的函数 foo() 接受两个参数：b 和 c。因此，b 将在 W0 中，c 将在 W1 中。

为什么是 W 而不是 X？因为参数是 32 位类型，因此我们只需要一个 W 寄存器。

> 在 C++ 中，X0 用于传递指向被调用函数的隐式 this 指针。

接下来，PCS 定义了哪些寄存器可以被破坏，哪些寄存器不能被破坏。如果一个寄存器可以被破坏，那么被调用的函数可以在无需恢复的情况下覆盖它，正如这张 PCS 寄存器规则表所示：

| 寄存器 | 用途 |
| --- | --- |
| X0–X7 | 参数与结果寄存器（X0–X7） |
| X8 | XR，间接结果寄存器 |
| X9–X15 | 可破坏寄存器（X9–X15） |
| X16 | IP0，过程内调用可破坏寄存器 |
| X17 | IP1，过程内调用可破坏寄存器 |
| X18 | PR，平台寄存器 |
| X19–X23 | 被调用者保存寄存器（X19–X23） |
| X24–X28 | 被调用者保存寄存器（X24–X28） |
| X29 | FP，帧指针 |
| X30 | LR，链接寄存器 |

例如，函数 foo() 可以使用寄存器 X0 到 X15 而无需保存它们的值。然而，如果 foo() 想使用 X19 到 X28，它必须先将它们保存到栈中，然后在返回前从栈中恢复。

一些寄存器在 PCS 中具有特殊意义：

- **XR** —— 这是一个间接结果寄存器。如果 foo() 返回一个结构体，那么结构体的内存将由调用者（前面例子中的 main()）分配。XR 是指向调用者分配的、用于返回结构体的内存的指针。
- **IP0 和 IP1** —— 这些寄存器是过程内调用可破坏寄存器（intra-procedure-call corruptible）。这些寄存器可以在函数被调用到到达函数第一条指令之间的时间内被破坏。这些寄存器被链接器用来在调用者和被调用者之间插入 veneer。Veneer 是小段代码。最常见的例子是分支范围扩展。A64 中的分支指令范围有限。如果目标超出该范围，那么链接器需要生成一个 veneer 来扩展分支的范围。
- **FP** —— 帧指针（Frame pointer）。
- **LR** —— X30 是函数调用的链接寄存器（LR）。

> 我们之前介绍了 ALU 标志，它们用于条件分支和条件选择。PCS 规定 ALU 标志不需要在函数调用之间被保存。

浮点寄存器也有一套类似的规则：

| 寄存器 | 用途 |
| --- | --- |
| D0–D7 | 参数与结果寄存器（D0–D7） |
| D8–D15 | 被调用者保存寄存器（D8–D15） |
| D16–D31 | 被调用者保存寄存器（D16–D31） |

## 29. 系统调用

有时软件需要向更有特权的实体请求一个功能。这可能发生在例如应用程序请求操作系统打开文件时。

![图 29-1：应用程序请求示例](../../asset/figure29-1-application-request.png)

*图 29-1：应用程序请求示例*

在 A64 中，有专门的指令用于进行此类系统调用。这些指令会引起异常，从而允许受控地进入更有特权的异常级别。

- **SVC** 超级用户调用（Supervisor call），引起面向 EL1 的异常。由应用程序用来调用操作系统。
- **HVC** 虚拟机监控器调用（Hypervisor call），引起面向 EL2 的异常。由操作系统用来调用虚拟机监控器，在 EL0 不可用。
- **SMC** 安全监控器调用（Secure monitor call），引起面向 EL3 的异常。由操作系统或虚拟机监控器用来调用 EL3 固件，在 EL0 不可用。

如果异常从高于目标异常级别的异常级别执行，那么异常会被送入当前异常级别。这意味着 EL2 处的 SVC 会导致进入 EL2 的异常。类似地，EL3 处的 HVC 会导致进入 EL3 的异常。这与“异常永远不会使处理器失去特权”的规则一致。

## 30. 知识自测

回答以下问题来检验你的知识。

**根据 PCS，对于函数 `uint32_t foo(uint64_t a, uint64_t b)`，哪些寄存器将用于传入 a 和 b，并返回结果？**

a 将在 X0 中传递，b 将在 X1 中传递。结果将在 W0 中返回。

**哪条指令执行 D0 和 D1 的 64 位浮点加法，然后将结果放入 D5？**

```asm
FADD D5, D0, D1
```

**这条指令做什么？`LDRSH W0, [X1, #8]`**

它从地址 X1+8 加载 16 位，并将结果符号扩展到 32 位，将结果放入 W0。

**哪条指令最常用于函数返回？**

RET

**调用函数时，哪个寄存器用于存储返回地址？**

X30，也可以被称为 LR。

**在应用程序中执行 SVC 指令会做什么？**

它会引起一个异常，导致进入操作系统。

**执行 `SUB W5, W8, W4` 后，X5 的上 32 位是什么？**

0（零）。每当写入一个 W 寄存器时，所映射 X 寄存器的上 32 位都会被清零。
